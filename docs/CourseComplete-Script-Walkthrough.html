How to read this document

This is a different kind of script from the others in the series. Those are element sweeps: many small tests, each asserting one thing. This one is a robot learner — a single test that opens a course and works through it until the platform says it is finished. Almost all of its 3,195 lines are the machinery that makes that possible.

So the structure follows the machinery rather than a list of tests. Section 3 diagrams the eight steps the one test takes; Sections 5 to 10 open up the interesting ones. Section 11 is the honest accounting: what a green run does and does not prove.

Line numbers in this document are live Every reference points at tests/CourseComplete.spec.ts as it stands today — 3,195 lines, including the per-line explanatory comments carried across the suite. They are safe to click through to.
A note on scale At 3,195 lines this is the largest file in the suite by a wide margin — roughly six times the size of the Course TOC spec, for a twentieth of the test count. That ratio is the story: driving a course to completion means handling every module type, every assessment shape, and every way the platform can stall, and none of that can be expressed as an assertion.

1   What this script does

It behaves like a learner who is determined to finish. It searches for a course, opens it, and then works through every module — watching videos, paging PDFs, scrolling content, and answering assessments correctly — until the platform shows the Congratulations screen.

Everything else in the suite checks that a page renders. This one checks that the product actually works end to end, which is a different and much harder question. A course only marks a module complete when the platform's own progress calls say so, and a graded assessment only completes when the pass mark is met. There is no way to fake either.

The four things that make it hard

Modules are gated
  • Later modules stay locked until earlier ones register as complete
  • So the order of work is decided by the platform, not the script
  • Clicking "Next" repeatedly just loops through the same units
Assessments must be passed
  • Answering "A" every time fails the pass mark
  • A failed assessment never marks its module complete
  • So the script has to know the right answers
Nothing is uniform
  • Four module types, detected rather than declared
  • Radio and checkbox questions, mixed within one quiz
  • Option order is shuffled on every render

Where it gets the answers

This is the part of the script people ask about first. Sphere prefetches a JSON file for each assessment, and that file carries an isCorrect flag on every option. The script listens for those responses and files them by resource id. Where the copy the browser receives has had its flags stripped — which graded assessments do deliberately — it goes to the published artifact on S3, which still carries them. Only when neither source yields a usable key does it fall back to asking Gemini.

Section 7 diagrams that ladder and Section 8 covers the plumbing. The short version is that the AI is the last resort, not the mechanism — on a normal published course it is never called at all.

This is a test account doing coursework, not a person Worth being explicit, because the script does real things to real data: it enrols, completes modules, submits assessment answers and generates a certificate on whichever account it is pointed at. It is meant for a test learner on a test environment. The one place it deliberately holds back is the ratings popup — handleCompletionPopups() closes it with the X rather than submitting a rating, so a run never leaves a fabricated review on a real course.

5   The sidebar-driven loop

The single most important design decision in the file, and the source says why in one line: "Blindly clicking Next just loops through the units."

A course player has a Next button, and the obvious way to complete a course is to keep pressing it. That does not work here. Sphere's player advances within a unit, so pressing Next walks the same handful of screens forever while the module list stays untouched. Worse, it gives no way to know when you are done.

So the script drives from the sidebar instead — the module tree that is the platform's own statement of what exists, what is finished, and what is still locked. Every iteration re-reads it, decides what to open, opens it, and then re-reads it again to ask whether anything actually changed.

What one sidebar node tells you

readModules() (line 2653) runs inside the browser and turns every mat-tree-node into a plain object. Four of its fields are read from markup that was never designed to be read this way:

FieldHow it is derivedWhy that way
done /check/.test(iconTxt)
&& !/outline/.test(iconTxt)		 Material icons render their name as ligature text, so the icon is readable — but check_circle_outline means "not done" and contains the word "check". Excluding the outline variant is the whole correctness of the completion check.
locked /\block\b/.test(iconTxt)
|| /\bdisabled\b/.test(cls)		 A lock icon or a disabled class. Either can carry the state depending on build.
active /content-active|li-active/ Two class names, because the player has shipped both.
resourceId extractResourceId(href) The do_… id parsed out of the node's router link. This is the ground truth for "did we land on the module we clicked" — see below.

Note that the class list is built from both the node and its inner anchor (`${el.className} ${a?.className}`), because the state lives on one or the other depending on version. And the whole thing ends in .catch(() => []): an unreadable sidebar yields an empty list, which the loop treats as "no sidebar" and falls back to processing whatever is on screen.

The bug that made openModule() necessary Clicking a sidebar link is not enough. The player is a single-page app, so the previous viewer stays mounted for a beat after the click. The original code would click a quiz, immediately detect the still-showing video, complete that video a second time, credit it to the quiz, and then blame the quiz for never registering. The doc comment above it, at line 2699, records exactly this.

The fix is to treat the URL as the arbiter. openModule() reads the target do_… id from the node's href, clicks, then polls for up to six seconds for the URL to actually name that resource. If the click did not navigate it goes to the href directly, polls again, and only then gives up — returning false so the caller can charge an attempt rather than process the wrong module.

Three ways the loop can get stuck, and what it does about each

SituationResponseWhy not just stop
A module opens but never registers as complete Charge an attempt to that module by name. After 2 attempts the picker skips it and moves to the next unfinished one. A single stuck module used to end the whole run. Now the run continues and only stops once every remaining module is exhausted — so one broken video no longer hides the state of the other fifteen.
Everything left is locked Nudge Next, reload if the page drifted off the overview, re-read the sidebar. Up to 4 times. The final gated unit often unlocks a beat after its prerequisites register, or needs a Next nudge to enter. Conceding immediately would fail a course that was about to finish.
No sidebar at all Process whatever is on screen; give up after 3 consecutive steps with no progress. With no module list there is nothing to attribute a stall to, so the old global rule is the only one available.

Each of these writes a line into reportWarnings as well as the console, so the HTML report at the end names the modules that would not complete rather than just saying the course did not finish.

// line 2939 — when unlocked modules remain but all have hit the cap
console.log(`\n🛑 These modules would not register as complete after ${MODULE_MAX_ATTEMPTS} attempts each:`);
unlocked.forEach((m) => console.log(`     • ${m.text}`));
Why the loop counts steps rather than modules for (let step = 1; step <= MAX_MODULES; step++) — the comment on line 2904 is explicit that these are steps, not modules. A retry spends one, a lock nudge spends one, an open failure spends one. Fifty is therefore comfortably more than any real course needs while still being a hard stop: the worst case is fifty iterations, not fifty modules each retried twice.

6   Module detection and the handlers

Sphere does not tell the script what kind of module it just opened. detectModuleType() works it out, and gets it wrong at some cost — a video handled as content is never watched, and never completes.

Why the URL is not enough

Three routes are unambiguous: /viewer/pdf means PDF, /viewer/video means video, /viewer/html means content. The problem is the fourth. Sphere serves course intro pages from /viewer/quiz/ too, so the quiz route is the one route that has to be verified rather than trusted.

For that case the function does three things in order of confidence:

  1. Check the captured answer keys first. If the interceptor filed a quiz JSON under this exact resource id, the module is an assessment — the platform fetched its questions. This is the strongest possible signal and it short-circuits everything below.
  2. Gather seven DOM signals in one round trip. A "Start Now" button, the radio count, the checkbox count, a "N Questions" + "N Minutes" pair, a canvas count, a PDF iframe, and whether the only heading is "Introduction" or "Overview".
  3. Let content beat the route. PDF markers win outright — a canvas or a PDF iframe on a quiz URL is treated as a PDF, and the run logs that it did so. An Intro heading with no quiz controls at all is treated as content. Any single quiz signal is enough to call it an assessment.

If none of that resolves — a quiz URL with no quiz indicators anywhere — it returns content and says so in the log. Content is the safe default: handling it just scrolls the page, which is harmless if the guess was wrong.

The four handlers

HandlerLineWhat it does, and what it is really trying to trigger
handleVideo520 Six stages, and every one of them exists to make the platform record a view. Wait for the <video> element (30 s) → wait for metadata so the duration is known, calling .load() if the browser is being lazy (60 s) → wait for enough buffer to play → mute and play, because muting is what makes browsers permit programmatic autoplay → seek to half a second before the end so the ended event still fires naturally → await that event, with a 15-second safety net. Returns whether the metadata ever loaded; a false becomes a report warning, not a failure.
handlePdf619 Clicks the viewer's own chevron_right up to 60 times, stopping when it disappears or goes disabled. The outer module Next button stays disabled until every page has been turned, so this is not cosmetic — it is the completion condition. Clicks are forced because the viewer overlay intercepts them.
handleContent642 Scrolls to the bottom (which is what registers the page as read), back to the top so inner controls are in view, then flips up to 30 inner page-turn chevrons if the content has them.
handleAssessment669 The large one — Section 7.
The video handler is the clearest example of the script's whole approach It would be far simpler to call video.currentTime = video.duration and move on. That does not work: the platform listens for real playback events, so the script has to mute the element (to get autoplay permission), start it, seek to just short of the end (so ended fires naturally rather than being skipped past), and then wait for the event. Every one of those steps is a workaround for how browsers and the platform actually behave, and none of it would be discoverable from the DOM alone.

7   Answering an assessment (continued)

The line that tells you which tier a run took

handleAssessment() announces its strategy before it reads a single question, and this is the most useful line in a run's log:

📝 ASSESSMENT — using answer key from the published artifact for do_1134204940…
📝 ASSESSMENT — every key for do_1134204940… is POISONED (all isCorrect: false) — using Gemini AI
📝 ASSESSMENT — no answer key for do_1134204940…, will use Gemini AI

If every assessment in a run prints the first form, the AI was never called and the run cost nothing but time. If any prints the second or third, the run depended on GEMINI_API_KEY, and Section 9's quota limits apply.

Counting the questions is harder than it looks

The obvious source is the on-screen "3 / 12" counter. The source rejects it, and the reason is worth quoting: the regex /\d+\/\d+/ can match a value inside the question itself — a blood-pressure reading of "100/70" makes the script believe there are 70 questions, and it then walks off the end of the assessment.

So the count comes from the key when there is one, even a poisoned one — a poisoned key has lost its answers but still knows exactly how many questions this assessment holds. The counter is only the fallback, and a hard-coded 5 the fallback's fallback:

const total = capturedKey && capturedKey.questions.length > 0
  ? capturedKey.questions.length
  : counterN || 5;

There is a safety net for the other direction too. If the answering loop reaches a question with no text and no options, it concludes the assessment really has ended and stops, rather than clicking Next into nothing.

When the key cannot answer one question

Three things can go wrong for a single question even with a good key: the matcher finds no entry for this stem, the matched entry flags nothing correct, or none of its correct options can be found on screen. The script's response to all three is the same, and it is a deliberate change from how it used to behave:

Ask the AI rather than defaulting to A "A wrong answer costs the pass mark, and the module only completes when the assessment is passed." Falling back to option A is free but actively harmful — it turns a recoverable gap into a failed assessment and an incomplete module. So answerWithKey() carries a small askGemini() closure and calls it in all three cases, logging why. Option A remains the fallback only when nothing at all could be scraped from the screen.

Mapping an answer onto the screen

The key gives answers as option text. Sphere shuffles option order on every render, so position is meaningless and text is all there is. Three helpers do the work:

HelperLineWhat it contributes
stripHtml1177The key's option text is HTML; the screen's is plain. This levels them.
normalizeText1183Collapses case, spacing and punctuation, which differ between the JSON and the rendered DOM.
findBestOptionMatch1194Fuzzy-matches one key option against the list on screen and returns its index, or -1.

Anything the key claims but the screen does not show is reported rather than silently dropped — the log prints the JSON's text verbatim, so a mismatch between the published artifact and the rendered quiz is visible instead of becoming a mystery wrong answer.

Radio, checkbox, and the field that settles it

A radio question takes exactly one answer; a checkbox question needs every correct option ticked or the mark is lost. Usually the DOM makes the type obvious. When it does not, the script trusts the artifact's own multiSelection field:

// the artifact says whether this is select-all-that-apply
if (scraped.inputType === 'unknown' && match.multiSelection) questionType = 'checkbox';

The type comment at lines 102–103 calls this "the AUTHORITATIVE answer to how many options should I tick — far more reliable than guessing from the on-screen control type", and that is right: the control can render ambiguously, but the content model cannot.

8   The answer-key plumbing

Five small functions and two Maps. Together they are the reason the AI is usually never called.

The interceptor

Sphere prefetches a JSON file for every assessment in a course, in bulk, as soon as the course opens. setupQuizKeyInterceptor() (line 282) attaches a page.on('response') listener that watches for them:

// only artifact JSON, of either naming convention
if (!/\/content\/[^/]+\/artifact\/.*_(quiz|assessment)\.json/i.test(url)) return;
if (!res.ok()) return;
// file it under its own resource id, but only if it actually holds questions
if (Array.isArray(json?.questions) && json.questions.length > 0) capturedKeys.set(resourceId, json);

Two design points are worth drawing out. It is a Map keyed by resource id, not a single slot — a course has many assessments and they arrive together, so each has to be filed under its own id or they overwrite one another. And the whole body is wrapped in a try that swallows parse errors silently: this is an opportunistic capture running inside a response handler, and a malformed body must not break the page.

This is why Step 2 comes before Step 3 The interceptor is attached before the course is opened. Attach it afterwards and the prefetch has already happened — the responses are gone, and every assessment falls through to the AI. It is one line in the test body and the comment beside it says only "Order matters", which is exactly right.

One regex, two jobs

extractResourceId() (line 272) pulls a do_… id out of a URL:

url.match(/(?:viewer\/\w+\/|content\/)(do_\w+)/)

The \w+ in viewer/\w+/ is doing quiet work. Matching every viewer type rather than just quiz is what lets openModule() confirm it landed on a video or a PDF, not only on an assessment — the same function serves both the answer-key lookup and the navigation check.

Going around the stripped copy

Graded assessments are served to the browser with their isCorrect flags removed. The published artifact on S3 still has them, and fetchAnswerKeyFromArtifact() (line 334) goes and gets it:

GET /apis/proxies/v8/action/content/v3/hierarchy/<do_id>?hierarchyType=detail
  → result.content.artifactUrl → { timeLimit, isAssessment, questions[] }

It runs inside the page rather than from Node, so the session cookies ride along without the script having to reconstruct them. Results are cached in hierarchyKeys — and that cache stores null as well as keys, which is why the code checks .has() rather than reading the value: an assessment with no artifact should be looked up once, not once per re-attempt.

The poison rule

isAnswerKeyPoisoned() (line 414) is four lines of logic with one judgement call in it:

const poisoned = key.questions.filter((q) => q.options.every((o) => o.isCorrect === false)).length;
return poisoned / total >= 0.8;
ChoiceWhy
Count questions where every option is falseThat is the signature of a stripped key: the questions and options survive, only the flags are gone.
80%, not 100%A threshold rather than "all", so a handful of genuinely-unflagged questions does not throw away an otherwise perfectly good key. The same rule is used in the competency suite.
An empty key counts as poisonedA key with no questions is exactly as useless as one with no answers, and treating them alike means the caller has one condition to check rather than two.

Keeping the questions even when the answers are gone

The subtlest part of handleAssessment() is what it does with a key it has just rejected. A poisoned key is useless for answering but still holds every question and option — so it is kept anyway, under a different name:

const answerKey = usable(artifactKey) ?? usable(interceptedKey);
// even a stripped key still knows the questions — keep the richer of the two
const capturedKey = answerKey ?? (artifactKey.questions.length >= interceptedKey.questions.length
  ? artifactKey : interceptedKey);

capturedKey is what makes Tier 2 possible: it supplies the question count, and it supplies the text of every question and option for the single batched request to Gemini. Without it the script would be back to scraping questions one screen at a time.

9   The Gemini fallback

Five functions and two pieces of state, all of them shaped by one constraint: the free tier allows 20 requests per day per model.

That number is what dictates the whole design. A single twenty-question assessment answered one question at a time would exhaust the day's quota by itself. So when a key is poisoned — the common case — the entire assessment goes out in one request, built from the key's own question and option text.

The call

callGemini() (line 1815) makes one REST call and returns a result object rather than throwing, because a network failure here is a normal outcome, not an exception. Three details in the request body:

SettingWhy
temperature: 0Deterministic. The same assessment should produce the same answers on a re-run.
topP: 1Keeps the full distribution available, so temperature 0 picks the genuinely most likely token rather than one from a truncated set.
thinkingBudget: 0Applied to the main flash model only. The reasoning in the source is exact: "These are recall questions, not reasoning puzzles, so the budget is wasted latency."

Telling the two kinds of 429 apart

A rate-limit response can mean two very different things, and the script distinguishes them from the error body:

Per-minute — worth waiting out
  • The API usually reports the delay; the script parses it from either retry in Ns or "retryDelay": "Ns"
  • No delay given? Wait GEMINI_RETRY_WAIT_MS (20 s)
  • Capped at GEMINI_MAX_RETRY_WAIT_MS (65 s) so a long suggested delay cannot stall the run
Per-day — waiting cannot help
  • Detected by /PerDay/i in the quota id
  • Sets the module-level flag geminiDailyExhausted (line 1861)
  • Every later request is skipped outright, with a plain message — rather than the run spending minutes discovering the same thing repeatedly

Model fallback and throttle

geminiAsk() (line 1867) wraps the call with the retry policy and a model fallback: gemini-2.5-flash first, gemini-2.5-flash-lite when the primary is rate-limited. Because the two models have separate quotas, that fallback effectively doubles the day's budget. In front of all of it, throttleGemini() (line 1803) simply sleeps so that no two calls are closer than 6.5 seconds — sized for 10 requests per minute, and skipped on the very first call.

The cache is what makes re-attempts free

geminiAnswerCache (line 977) maps a resource id to a map of normalized question stem → correct option texts. Both halves of that shape matter:

  1. Keyed by resource id, so a second attempt at the same assessment reuses the answers instead of spending quota again. The log says so explicitly: ♻️ Reusing cached Gemini answers … (no extra quota).
  2. Values are option TEXTS, not letters. Sphere shuffles the options between attempts, so a cached "B" would be wrong the second time round. Texts survive the shuffle and are re-matched onto the screen by the same fuzzy matcher Tier 1 uses.
The honest position on using an AI inside a test It is a fallback for a deliberate obstacle, not a shortcut. On a normal published course the answer key is intact and Gemini is never called; the log makes which path was taken unambiguous. Where it is called, the run's correctness depends on a third-party model being right about clinical multiple-choice questions — which is worth knowing when reading a green result. Section 11 puts that in the list of things green does not prove.

10   Completion, certificate, report

The loop ends. Now the script has to decide whether the course is actually finished — and it asks the question five different ways.

Five signals, any one of which counts

const completionMarker =
  pageClosed ||
  sawPopups ||
  allModulesComplete ||
  progressPct === 100 ||
  (await isCourseComplete(page).catch(() => false));

The source calls this generosity deliberate: "the app surfaces completion differently by course type." Some courses show a popup, some just fill the progress bar, some close the tab. Requiring one specific signal would fail courses that had genuinely completed.

Fourteen ways to say "you finished"

isCourseComplete() (line 2205) tries fourteen regexes, in English and Hindi, each with a 300 ms timeout — it runs on every loop iteration, so it has to stay cheap. Two of them show the care that went into the list:

PatternThe detail
/congratulations[\s!,]/iThe trailing character class is deliberate — it stops the word matching inside a longer sentence in a module description.

/rate\s+(this|the)\s+course/iA rating prompt only ever appears after completion, which makes it a reliable marker even though it says nothing about completion directly.
/बधाई/iHindi. The platform is bilingual and so is the completion screen.
It closes the ratings popup instead of using it handleCompletionPopups() reads the popup, logs every button it offers, and then dismisses it with the X — with a comment that says why: "the run must not leave a fake review on a real course." Submitting a rating would be the easier path and would arguably exercise more of the product. Not doing it is the right call, and it is the kind of decision worth making explicitly rather than by omission.

The certificate, and when it is not attempted

Step 7 has two gates, and both must pass: the course must have completed, and a certificate must have been detected back at Step 3b. Failing either just prints a line.

Not completeSkipped with ⏭️ needs Congratulations/Ratings first — the control will not be there, so trying would only add noise.

The generation flow itself is the fiddliest code in the file. The dialog draws the certificate onto a <canvas> before the download becomes available, so the script waits for that canvas, then registers the download listener and clicks at the same time via Promise.all, with a 25-second window because generating and streaming a certificate is genuinely slow. If the app answers with "certificate is taking time to generate" — one of six wordings it recognises — it closes the tab, waits twenty seconds, and starts the whole attempt again.

Downloads are saved as test-reports/certificates/Certificate_<CourseSlug>.<ext>, with jfif and jpeg both normalised to jpg. A failure anywhere in Step 7 is caught and logged — never thrown, because the course still completed and that is what the test is about.

The report

Step 8 writes test-reports/course-reports/CourseReport_<slug>_<timestamp>.html through generateCourseReport(). It carries the wall time, the module types in order, every warning the loop collected, the assessment table, the completion verdict, the certificate outcome and the final URL. Like Step 7 it is wrapped in a try: a report-writing failure must not fail a run that actually passed.

11   What green actually proves

One expect() in 3,195 lines. It is worth being precise about what it does and does not cover.

expect(
  completionMarker,
  `Course did not reach the Congratulations/Ratings completion popup (touched ${log.length} modules).
   See the course report for where it stopped.`,
).toBe(true);

The failure message is doing real work. It names how many modules were touched and points at the report, so a red run can be diagnosed without re-running an hour-long test — which matters more here than in any other spec in the suite.

Green means this
  • The course was found by name and opened
  • Start or Resume worked
  • Modules were opened in the platform's own order, respecting gating
  • Videos played to their ended event
  • PDFs were paged to the last page
  • Every graded assessment was passed — a failed one never marks its module complete
  • The platform reached a completion state by at least one of five signals
Green does not mean this
  • That the certificate downloaded — Step 7 never throws
  • That the report was written — Step 8 never throws
  • That every answer was correct, only that the pass mark was met
  • That AI-sourced answers were right, where Tier 2 or 3 was used
  • That no module was skipped after exhausting its attempts — that is a warning, not a failure
  • That the run was quick, or that a learner would have had a good time
A closed page counts as success pageClosed is the first of the five signals, and it is true whenever the tab is gone. That is right for the common case — the completion popup really does close the tab on some courses — but it means a browser crash at the wrong moment reads as a completed course. Nothing distinguishes "the popup closed us" from "the renderer died".

It is a narrow window and the other four signals usually corroborate, but if this run is being used as a release gate it is worth tightening: requiring pageClosed to be accompanied by allModulesComplete, or by a progress read taken before the tab went away, would close it without weakening the generosity that the five-signal design is there to provide.

How this compares with the rest of the suite

SuiteTestsAssertionsWhat a green run is evidence of
Course Completion this one11The product worked end to end for one learner on one course. Broad, deep, and slow.
Course TOC2115 + 3Every control on one page renders and responds. Narrow, precise, and fast.

The two ends of that table are complements, not competitors. The element sweeps tell you what broke; this one tells you whether a learner could finish. A suite with only the first kind can be entirely green while the product is unusable, and a suite with only this one can tell you something is wrong without telling you where.

Reading the console

This is the one spec where the log matters more than the result line, because the result line is a single boolean. The markers worth grepping for:

MarkLineWhat it tells you
🔑Captured answer key for do_… (13 questions)The interceptor is working. One per assessment in the course, printed early, before any module opens.
📝ASSESSMENT — using answer key from the published artifactWhich tier this assessment took. If every one of these says "published artifact", the AI was never called.
📚Step 7 — 4/11 modules doneThe progress banner, one per loop iteration. The fastest way to see where a run stalled.

Failure modes

SymptomCauseFix
No course selected, immediately COURSE_NAME is unset. Unlike the TOC spec this throws rather than skipping. Use npm run run:course, or set it. The error text names both routes.
Could not find course "…" The title did not match anything on this environment. npm run courses:list. The matcher compares whole result titles, not prefixes, precisely so that a near-miss fails loudly rather than opening the wrong course.
No 🔑 lines at all, and every assessment uses Gemini The interceptor was attached after the prefetch, or the artifact URL pattern changed. Confirm Step 2 still runs before Step 3. If the URLs have changed, the regex at line 287 is the single place to update.
An assessment loops, re-attempting and failing Answers are wrong. Either the key mapped badly onto the screen, or the AI answered incorrectly. The log prints every option lettered and every pick — compare them by eye. Watch for the ⚠️ N/M not found on screen line, which means the key's text no longer matches the rendered options.
🛑 These modules would not register Those modules genuinely did not complete after two attempts each. The most valuable failure this spec produces. Open the named module by hand and watch whether its progress call fires.
🔒 Remaining modules stay LOCKED Gating never released after four nudges. Usually a genuine prerequisite that never registered — check the modules before the locked ones, not the locked ones themselves.
Gemini stops answering mid-run The per-day quota is gone. geminiDailyExhausted is set and later requests are skipped rather than retried. Wait for the quota to reset, or run against a course whose key is not poisoned. The model fallback already gives two separate daily budgets.
The run hits the 60-minute timeout Usually a module that opens but never completes, spending its attempts slowly. Read the 📚 banners: the last one names the step and the done count, which brackets the problem to one module.
Certificate never appears Generation is genuinely slow, or the course has none. Not a failure — Step 7 only logs. The summary line distinguishes "attached but generation not confirmed" from "none".
A video module warns load timeout The metadata never loaded within 60 s. Recorded as a report warning, not a failure. Repeated across runs it is a CDN or encoding problem worth raising.
Where to start when a run goes red Open the course report first, not the Playwright report. It carries the warnings, the module timeline and the assessment table in one page — and the assertion message points you there by design, because re-running to investigate costs an hour.
