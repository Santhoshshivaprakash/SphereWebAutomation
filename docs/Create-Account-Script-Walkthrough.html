1   What this script does

It is the end-to-end proof that a brand-new person can create a Sphere account unaided — and it is the factory that mints the fresh, logged-in users every other suite depends on.

The script exercises the complete public signup journey: Select Language → Personal Details → OTP verification → Name confirmation → Terms & Conditions → logged-in Home. It covers both login methods the portal offers (OTP and password), validates the form before submitting it, and checks the screens render on phone, tablet and desktop.

The OTP is not stubbed. The script registers a real @yopmail.com address, then reads the real verification mail out of that inbox, so the mail-delivery leg of the journey is covered too.

The three jobs it performs

Validates
  • Language screen renders, is single-choice, gates Next
  • Form gates Next until filled
  • Field accepts email and phone
  • Layout survives 390px → 1440px
Proves end-to-end
  • Email + OTP signup reaches Home
  • Phone + password signup completes
  • Mail actually arrives and carries a usable OTP
  • T&C accept unlocks the app
Produces
  • .last-registered-email.json
  • .auth/fresh-user.json — live session
  • .auth/fresh-user-email.json
  • Console trail of every email used

Where it runs, and why not localhost

The spec pins its own default target instead of inheriting the shared BASE_URL:

// tests/create-account.spec.ts:22
const BASE_URL = process.env.BASE_URL ?? 'https://sphere.aastrika.org';

Signup cannot run against the localhost prod-mirror — that mirror has no mail path and no user-provisioning backend, so an OTP would never arrive. This flow therefore targets staging by default. Passing BASE_URL still overrides it if you need to point somewhere else.

2.3   How a fresh identity is generated

// :38 — a new inbox on every call, 90,000 possible addresses
function generateEmail() {
  const suffix = Math.floor(10000 + Math.random() * 90000);
  return `testautomation${suffix}@yopmail.com`;   // e.g. testautomation48213@yopmail.com
}

// :43 — phone path walks DOWN from 9999999999 on each collision
function generatePhone(seed = 0) {
  return String(parseInt(DEFAULT_PHONE) - seed);    // 9999999999, 9999999998, …
}
Why email is the automation identity, not phone A phone number can register exactly one account, its SMS OTP cannot be read by automation, and a real-looking number risks texting a stranger. A yopmail address gives an unlimited supply of single-use identities whose OTP the script can read — which is precisely how the "a number can never be reused" limitation is overcome.

Inside selectLanguageByIndex — three escalating strategies

Angular Material radios are not plain inputs; the real <input> sits under a styled wrapper that can swallow a click. The helper therefore escalates, verifying after each attempt and stopping as soon as the input reports checked:

  1. Click the wrapper. mat-radio-button at the index, scrolled into view, with { force: true }. Wait 600 ms, then read input[type=radio].nth(idx).isChecked(). If true, done.
  2. Click the inner ripple. Falls through to .mdc-radio inside that wrapper — the element Material actually binds the handler to. Wait 500 ms, re-check.
  3. Drive the DOM directly. A page.evaluate clicks the raw input, and if it still is not checked, sets .checked = true and dispatches input and change events so Angular's form control notices.

The helper returns the final checked state rather than throwing, which is why each test asserts on its return value instead of trusting the click.

Index is fine here, label is required later These tests use index deliberately — they are testing radio mechanics, so position is the right handle. But advancePastLanguageScreen (:101), which picks the language the account is actually created in, matches on /english|अंग्रेजी/i instead. Staging renders this screen in Hindi, so a reordered list would silently sign the user up in Hindi and break every English selector downstream.

Why the inputs are addressed by position

// :120 — the three visible text fields, in DOM order
function formInputs(page) {
  return page.locator('input:not([type="radio"]):not([type="hidden"]):not([type="password"])');
}
//   nth(0) → First name
//   nth(1) → Last name
//   nth(2) → Phone number / Email

The three exclusions are what make positional addressing safe. Dropping radio keeps the language and login-method controls out of the list; dropping hidden excludes Angular's internal fields; dropping password means the same helper still returns exactly three fields on the password screen, where two more inputs appear. clearFormInputs caps its loop at Math.min(count, 3) for the same reason.

The overlay-safe click

Submitting an OTP puts a full-screen loading .overlay over the page. It intercepts pointer events, so a plain click() throws "element intercepts pointer events" and the test fails on a flow that actually worked. The script handles it with a four-attempt loop:

for (let i = 0; i < 4 && !submitted; i++) {
  await page.locator('.overlay').first()
    .waitFor({ state: 'hidden', timeout: 5000 }).catch(() => {});  // let it clear
  try { await verifyBtn.click({ timeout: 6000 }); submitted = true; }
  catch {
    // enterOtp() pressed Enter — the form may ALREADY be submitted,
    // in which case the button is gone. That counts as success.
    if (!(await verifyBtn.isVisible().catch(() => false))) { submitted = true; break; }
    await page.waitForTimeout(1000);
  }
}

Why the OTP is typed twice

enterOtp (:393) targets input#code: if there are as many fields as digits it fills one digit each and presses Enter on the last, otherwise it fills a single field and presses Enter. Step 4 then re-reads the page for input[maxlength="1"] boxes and fills them again. The duplication is deliberate — some builds render the boxes without the #code id, and re-filling an already-correct field is harmless, while a half-filled OTP is not.

Every test guards on a closed page Tests 2–5 each open with if (sharedPage.isClosed()) { test.skip(...); return; }. In a serial block a crashed tab would otherwise turn one real failure into four confusing ones; skipping keeps the report pointed at the step that actually broke.

8   The OTP subsystem

The most failure-prone leg of the journey, and the one with the most engineering behind it.

The script cannot ask the server for the code — that would skip the mail-delivery leg it is meant to cover. So it reads the real inbox. Three independent readers are tried in order, and each one's failure is remembered so the final error names all three.

Figure 3 — Three readers, tried in order. Any layer returning a code short-circuits the rest; only an all-three failure raises, and it raises once with all three reasons.

8.1   How the code is recognised

Layer 1 filters on sender and subject before parsing, so a newsletter landing in the same inbox cannot be mistaken for a verification mail. The digits are then pulled with a two-stage regex that prefers the phrase form and only then falls back to any standalone 4–8 digit run:

const m = body.match(/is\s+(\d{4,8})/i) ?? body.match(/\b(\d{4,8})\b/);

Preferring "…is 483921" matters because mail bodies often carry other numbers — a year, a support phone, a ticket id — and a bare digit match would happily grab the wrong one.

8.2   Throttling — why the run deliberately goes slow

Yopmail does not rate-limit steady traffic; it flags bursts of automated inbox reads, and answers with a CAPTCHA that no layer can pass. Three independent gates keep the run under that threshold:

GateDefaultWhat it spaces out
YOPMAIL_MIN_GAP_MS6 sEvery single yopmail request, run-wide — each getInbox, each readMessage, each UI refresh click. Enforced by a module-level timestamp, so it holds across all signups in the run, not just within one.
YOPMAIL_POLL_MS7 sThe pause between poll attempts while waiting for the mail to land.
YOPMAIL_RETRIES8How many attempts each layer makes before giving up — fewer attempts, spaced further apart.
FETCH_CYCLE_GAP_MS12 sThe gap between two whole fetch cycles, which is the gap between two signups. Stops back-to-back registrations from bursting the inbox.

Both gates share one small primitive that simply sleeps for whatever remains of the minimum interval:

// :191
async function throttleGate(getLast, setLast, minGap) {
  const wait = minGap - (Date.now() - getLast());
  if (wait > 0) await new Promise((r) => setTimeout(r, wait));
  setLast(Date.now());
}
Budget the time A full run signs up three times. With the defaults, expect roughly 30–90 s per OTP fetch depending on how fast the mail arrives — which is why the OTP steps carry 180 s timeouts. If you are debugging something unrelated, --grep to the section you care about rather than waiting out all three.

Two selector lessons, both learned the hard way

Match by class, not by wording

Portal language is a per-account setting, and staging serves this screen in Hindi, where Accept reads स्वीकार करना. An anchored /^स्वीकार( करें)?$/ does not match that, so the button was never found and the terms were never accepted. button.accept-btn and button.decline-btn are identical in every language.

Detect the screen by route, not by text

Keying isOnTerms off the words "Terms of Use" produced false positives — that phrase also appears in the home page footer. The check now uses the route (/new-tnc|\/tnc\b|terms-and-cond|consent/) or the Decline + Accept control pair, which only ever coexist on the real terms screen.

Why the Decline detour was removed

An earlier version signed up, declined the terms, logged back in, and then accepted. It was dropped: it doubled the OTP fetches and therefore the runtime, and it made minting a fresh user fail whenever the public login page changed — without adding any coverage the positive path needs. Decline is now tested where it belongs, not on the critical path that every other suite depends on.

The hand-off, and who consumes it

// .auth/fresh-user.json       → full Playwright storageState (cookies + origins)
// .auth/fresh-user-email.json → { "email": "testautomation48213@yopmail.com", "timestamp": … }

// Consumed by tests/helpers/authedTest.ts when USE_FRESH_USER=1

The session is saved rather than the credentials, because a yopmail-email account is OTP-only — there is no password to log back in with. Capturing the live session is the only way a later suite can continue as this user.

Responsive Layout  ·  3 tests  ·  line 916  ·  parallel-safe creates no account

What it proves: the two screens a user must get through before any account exists render correctly from a small phone up to a desktop. This is the only non-serial block in the file — each test builds its own context at its own viewport, so nothing is shared and the three can run together.

ViewportSizeRepresents
Mobile390 × 844The dominant real-world case — a modern phone. The narrowest layout the signup form must survive.
Tablet768 × 1024The breakpoint where most responsive grids switch between stacked and side-by-side.
Desktop1440 × 900The design reference width.

What each of the three tests does

  1. Build an isolated context at that viewport. browser.newContext({ viewport: { width, height } }) then newPage(). A fresh context per viewport is what makes the block parallel-safe.
  2. Navigate. goToCreateAccount(page), including the login-redirect guard.
  3. Clear the language screen. selectLanguageByIndex(page, 0) then Next, waitForLoadState('networkidle') and 1200 ms.
  4. Assert the form rendered. expect(page.getByText(/create your account/i).first()).toBeVisible() — proof that both screens survived the narrower viewport and the form is reachable, not clipped or collapsed.
  5. Tear down. ctx.close() disposes the context and its page together.
Scope, honestly stated This is a smoke check for reachability, not a visual-regression test. It confirms the layout does not break badly enough to hide the form; it will not catch a mildly misaligned label or an overlapping icon. Pixel-level checks belong in the brand and Figma comparison suites.

13   Failure modes and fixes

SymptomMost likely causeWhat to do
Every spec fails to resolve Playwright was invoked from D:\Automation instead of SphereWebAutomation\. Change into SphereWebAutomation\ and re-run. This is the single most common cause of a whole-suite failure.
"OTP fetch failed across all layers" Yopmail served a CAPTCHA after a burst, or the mail never arrived. Read the aggregated error — it names all three layers' reasons. If Layer 1 mentions CAPTCHA, raise YOPMAIL_MIN_GAP_MS and FETCH_CYCLE_GAP_MS and re-run. Configure OTP_API_URL + OTP_EXTRACTION_KEY to make Layer 3 available as a real safety net.
Layer 2 logged as "skipped (no context)" fetchOtp was called without { context }. Pass the BrowserContext. Both in-file call sites already do; a new call site must too, or you silently run on two layers instead of three.
"OTP screen not detected" with a URL and body preview logged The app went somewhere else after Confirm name — often "already registered", or a server error on the signup POST. Read the logged body preview; it usually names the real problem. If the wording simply changed, add the new phrase to the 8-marker list at line 594.
Verify click throws "intercepts pointer events" The loading .overlay stayed up longer than the four retry attempts allowed. The backend is slow. Confirm staging is healthy; the retry loop is already the correct pattern, so widen its timeout rather than removing the guard.
Section 5 fails with onTerms === false Either the account did not actually get created, or the terms screen rendered in a language the text matcher missed. Check the logged URL first. If it is /app/new-tnc, the class-based selectors are the fix — match button.accept-btn, never the label.
Section 4 fails with phoneAccepted === false All 10 candidates from 9999999999 downward are already registered. Expected eventually — the pool is consumed one number per run. Widen the loop or change the DEFAULT_PHONE seed to an unused block.
Language screen never appears; page lands on Home The context carried a logged-in session, so the app redirected away from signup. Confirm the run is not reusing a storageState. beforeAll creates a clean context precisely to prevent this.
The whole account got created in Hindi Something selected index 0 on a screen where Hindi was listed first. Use advancePastLanguageScreen, which matches /english|अंग्रेजी/i by label. Reserve selectLanguageByIndex for the radio-mechanics tests in Section 1.
Four tests fail where one broke Normal serial behaviour — but check whether the tab crashed. The isClosed() guards convert the downstream tests to skips. Fix the first failure; the rest usually follow.

The one rule to keep Every selector in this script is chosen to survive a language change — matched by route, by class, or by a regex that covers both English and Hindi. When you add a selector, match the structure, not the words. The portal's language is a per-account setting, and the account this script creates may not be in yours.
