1   What this script does

It verifies that the login page presents every control a returning user needs, in both of its input modes — and it is the source of truth for the selectors the rest of the project logs in with.

/public/login is the gate every returning learner passes through. It offers two ways in — a one-time code or a password — plus a help modal, a create-account escape hatch and a forgotten-password path. This spec walks all of it: each control, each mode, each modal, plus responsive rendering and page health.

Its second, quieter job

This file is where the project's login selectors are proven — tests/helpers/login.ts says so in its own header: "Selectors mirror the ones verified in public-login.spec.ts." So a change that breaks a locator here breaks every authenticated suite downstream — and this spec is the cheapest place to find out. That is a large part of its value, and it explains the file's shape: broad locator coverage, shallow outcome assertions.

What it deliberately does not do

No test in this file asserts that a login succeeded The "Login" test fills real credentials, clicks the button, waits 2500 ms, then logs the resulting URL and any toast — there is no assertion about where the browser ended up. The same is true of "Get OTP", "Forgot Password?", "Create an Account" and the back arrow. This is by design (the suite owns no account whose state it can rely on), but it means a broken authentication backend would not turn this suite red. That assertion lives in tests/login-check.spec.ts.

The four things it verifies

Controls exist
  • Both mode radios, Get OTP, Login
  • Forgot Password, Create an Account
  • Page title names Sphere or Aastrika
Modes behave
  • Password mode reveals the password field
  • Toggling back to OTP removes it entirely
  • Password input is genuinely masked
Modal and health
  • Help opens the chat-support modal
  • Its X button really dismisses it

2   Configuration, helpers, credentials

2.1   Target and navigation

// tests/public-login.spec.ts:5
const BASE_URL   = process.env.BASE_URL ?? 'https://sphere.aastrika.org';
const PUBLIC_URL = `${BASE_URL}/public/login`;

// :49 — runs before all 29 tests
await page.goto(PUBLIC_URL);
await page.waitForLoadState('networkidle');

Note the wait condition: networkidle, not domcontentloaded. The login page is a small Angular shell whose controls appear only once its bootstrap requests settle, so waiting for the network to go quiet is what makes the very first assertion in each test reliable. It also makes each test's setup slower than the public home page's, which is an acceptable trade at 29 tests.

Unlike PublicPage.spec.ts, this file does not normalise the origin — a BASE_URL with a trailing slash produces a double-slashed URL. In practice Angular's router tolerates it, but it is a difference worth knowing if you point the suite somewhere unusual.

2.2   The four helpers

HelperLineWhat it solves
scrollAndClick:10 scrollIntoViewIfNeeded() then click(), unguarded. Used where a failure should surface.
identifierInput:19 Returns the phone/email box. The first <input> on this page is the OTP/Password radio, which cannot be filled — so a naive input.first() throws. This helper filters to text, email, tel and untyped inputs before taking the first.
helpControl:26 Returns the Help control. It is a clickable <div> wrapping a help-icon image, not a <button> — so getByRole('button') never finds it. Matches the exact text "Help", or any image with help in its alt.
safeClick:35 Wraps scrollAndClick in try/catch. On success it logs ✅ Clicked: <label>; on failure it logs a warning and the test continues. This one helper is why so much of the suite is present-only. 
// :35 — a click that can never fail the test
async function safeClick(page, locator, label) {
  try {
    await scrollAndClick(page, locator);
    console.log(`✅ Clicked: ${label}`);
  } catch (err) {
    console.log(`⚠️  Could not click ${label}: ${err.message.split('\n')[0]}`);
  }
}
Two helpers encode real discoveries about this page identifierInput and helpControl both exist because the obvious locator was wrong, and both carry a comment in the source explaining why. They are worth reading before writing any new test here: the first input is not the text box, and the Help control is not a button. Reuse the helpers rather than re-deriving the locators.

Because no test asserts the outcome of a submission, stale credentials do not fail the suite — they simply change what gets logged. That is consistent with the file's design, but it does mean the credentials can silently rot.

2.4   One thing this spec does not inherit from its sibling

No bilingual matching here PublicPage.spec.ts routes every text assertion through a tr() helper because the portal serves Hindi by default. This file has no equivalent — every matcher is an English-only regex (/login with otp/i, /get otp/i, /forgot password\??/i). On an environment rendering the login page in Hindi, the text-based assertions would not match. The suite passes today because the environments it runs against serve this page in English; if that changes, the fix is the same tr() pattern the sibling file already implements.

4   The three page states

Every test starts in the same state. Two groups use a nested beforeEach to move somewhere else first.

Figure 2 — Three states, two transitions. The nested beforeEach hooks are what let Groups 5 and 7 read as flat lists of element checks rather than repeating a setup click in every test.

Why the nested hooks matter

Without them, all five password tests and all four modal tests would each have to open their state by hand — nine repetitions of the same two lines, and nine places to update when the toggle's markup changes. The hooks put the setup in one place per group.

They also shift what a failure means. If scrollAndClick(getByText(/login with password/i)) throws in the Group 5 hook, all five tests in that group fail at once, all with the same hook error. That is the correct signal — the mode toggle is broken, not five separate controls — but it is worth recognising when reading a report: five reds from one cause.

Group 3 is the one that tests the transition itself Groups 5 and 7 use the transitions; Group 3 tests them. Its third test is the strongest assertion in the file about state — after toggling to password mode and back, it asserts expect(count).toBe(0) on input[type="password"]: the field must be gone from the DOM, not merely hidden. If Group 3 is green and Group 5 fails in its hook, the problem is the password screen, not the toggle.

5   Assertion depth

Nine tests click something that navigates or submits. Understanding where each one stops is the key to reading this suite.

Figure 3 — Every click test in this file reaches stage 3 and stops. Stage 4 is covered by login-check.spec.ts, which takes its credentials from the environment and asserts the browser left /public/.

What this means in practice A green run of this suite says: every control is present, correctly labelled, and clickable without throwing. It does not say the login works. When triaging an auth incident, this file tells you whether the page is intact; login-check.spec.ts tells you whether anyone can get in. Run both, in that order.

The Material icon trick in test 2

Angular Material renders icons as ligature text inside a <mat-icon>: the element literally contains the string chevron_left, which the icon font draws as an arrow. So the back button has no accessible name a human would recognise — but it does have matchable text:

page.getByRole('button').filter({ hasText: /chevron_left|arrow_back/i })
    .or(page.getByRole('button').first())    // fallback: the first button on the page
    .first();

The .or() fallback is a pragmatic hedge — if the icon is ever swapped for an SVG or an aria-label, the locator degrades to "the first button", which on this page is the back control. It keeps the test running, at the cost of possibly asserting on the wrong button if the header is ever reordered.

Why helpControl is a helper, not an inline locator

The source comment is explicit: the Help control is a clickable div with a "help-icon" img, not a <button>, so getByRole('button') will not find it. Because Group 7's beforeEach also needs to open the modal, the locator is factored out — one definition, two call sites, and a comment recording the discovery so nobody re-derives it.

Test 3 is the header's real assertion Tests 1 and 2 confirm the page is dressed correctly. Test 3 confirms something works — a click produces a modal, asserted, not logged. It is one of only two places in the whole file where a click's consequence is hard-asserted; the other is the modal's close button in Group 7.

Test 3 is the most precise assertion in the file toBe(0) on a locator count is a stronger statement than not.toBeVisible(). Why test 1 uses a different locator from tests 3 and 4

Test 1 leads with getByLabel(/phone number.*email/i) — the accessible label, which is the most semantically correct handle — and falls back to the type-based selector. Tests 3 and 4 call the identifierInput helper, which is type-based only. Both resolve to the same field on today's markup. Using the helper everywhere would be marginally more consistent and would put the "first input is the radio" knowledge in exactly one place.

Test 3 is the clearest hardening opportunity in the file

// :175 — as written, this cannot fail
const disabled = await getOtpBtn.isDisabled().catch(() => false);
console.log(`✅ Empty-state — Get OTP disabled: ${disabled}`);

// what it would take to make it real:
expect(disabled).toBe(true);

Whether the button is gated on input is genuine product behaviour with a definite correct answer, and unlike the navigation tests it needs no account and no backend. The ✅ in the log line is also slightly misleading — it prints regardless of what the value turned out to be.

What test 4 does and does not cover It proves the submit path is reachable: a valid identifier can be typed and the button accepts a click without throwing. It does not prove an OTP was requested, sent, or received — and it will log a perfectly normal-looking URL whether the request succeeded or returned a 500. End-to-end OTP delivery is covered by create-account.spec.ts and OTP.spec.ts, which read the real mailbox.

Test 2 is doing real security work

Asserting type === 'password' after filling the field confirms the browser's native masking is active. It is a small check with a real failure mode behind it: a field whose type was switched to text — by a mis-wired reveal toggle, say — would show the password on screen and, worse, expose it to any screen-capture or screen-sharing in progress. This is one of the few assertions in the file that would catch a genuine defect rather than a missing element.

Test 3's known weak point

if (eyeVisible) {
  await scrollAndClick(page, eyeIcon);
  // reads input index 1 — assumes the password box is the second input
  const afterType = await page.locator('input').nth(1).getAttribute('type').catch(() => null);
  console.log(`   Password input type after toggle: ${afterType}`);
}

Two things stand out. It reads input by raw index — and index 1 is a guess that holds only while the DOM order is radio, identifier, password. And the result is printed, not asserted, though the whole point of the toggle is that the type flips password → text: a definite, checkable outcome that would pair naturally with test 2.

Test 5 is where "present-only" matters most This test types a real email and a real password into the real login form of a live environment and clicks Login. Whatever happens next — success, "invalid credentials", a rate-limit, a 500 — the test passes and prints it. The captured toast is genuinely useful when reading a run by hand, but nothing gates on it. If you want this suite to notice that logins have stopped working, this is the test to change; if you want that coverage without changing this file, run npm run login:check, which asserts the browser left /public/.

The .filter({ visible: true }) in test 3

The source comment explains it: a hidden third-party chat widget elsewhere on the page also contains the text "chat with us". Without the filter, .first() could resolve to that invisible element, and the test would fail on a modal button that is perfectly fine. Popup handling, and why it cannot fail

const popupPromise = page.waitForEvent('popup', { timeout: 3000 }).catch(() => null);
await safeClick(page, waBtn, 'Chat with us on WhatsApp');

The listener is registered before the click — a popup opening faster than the listener attaches would be missed. The .catch(() => null) turns the 3 s timeout into a null rather than a rejection, so both branches are normal outcomes.

A modal that cannot be dismissed traps a user on a page they were trying to log in from — worth the hard assertion.

The loop

for (const c of cases) {
  await input.fill('');
  await input.fill(c.val);
  await page.waitForTimeout(150);
  const actual  = await input.inputValue();                      // what the field KEPT
  const enabled = await getOtpBtn.isEnabled().catch(() => true);  // did the gate open?
  const preview = actual.length > 40 ? `${actual.slice(0, 40)}...` : actual;
  console.log(`   • ${c.label.padEnd(25)} → accepted="${preview}" | Get OTP enabled=${enabled}`);
}

Two observations per payload: what survived the field's own filtering, and whether the button unlocked. The padEnd(25) aligns the output into a readable column, which is the point — this test's product is a table a human scans.

What the output looks like

   • empty                     → accepted="" | Get OTP enabled=false
   • single space              → accepted=" " | Get OTP enabled=true
   • single char               → accepted="a" | Get OTP enabled=true
   • 10-digit phone            → accepted="1234567890" | Get OTP enabled=true
   • phone with country code   → accepted="+919876543210" | Get OTP enabled=true
   • standard email            → accepted="test@example.com" | Get OTP enabled=true
   • special chars             → accepted="!@#$%^&*()" | Get OTP enabled=true
   • XSS payload               → accepted="<script>alert(1)</script>" | Get OTP enabled=true

Illustrative shape — the real values depend on the build under test.

Reading this test correctly A row showing enabled=true for single space or special chars is a finding — it means the client accepts an identifier that can never match an account, and the user learns that only after a round trip. But this test will not tell you: it prints the row and passes. The output is evidence for a human, and it is only worth generating if someone reads it.

The <script> row is a probe, not an XSS test. Seeing the payload echoed back into the input's value is expected and harmless — a real check would confirm the string is escaped where it is rendered, and nothing here does that. Treat it as a note that the field does no input sanitisation, which is normal for a text box.
If you want this to gate anything The cheapest meaningful assertion is on rows 1 and 2 — empty and whitespace-only must not enable Get OTP. Both are unambiguous, both need no backend, and both are already being measured. Everything else in the list is genuinely a judgement call about product intent, which is why logging is the honest default for them.

The one sentence version

A green run means the login page is intact and operable Every control is present and correctly labelled, both input modes work, the password is masked, the help modal opens and closes, and the page renders from 390px to 1440px. That is genuinely valuable — it is the fastest way to know a deploy did not break the gate every returning user passes through, and it is the check that protects the selectors every authenticated suite depends on.
A green run does not mean anyone can log in No assertion in this file examines where a click led. Run npm run login:check for that — it drives the same page through tests/helpers/login.ts with credentials from LOGIN_ID / LOGIN_PASSWORD, and asserts the browser left /public/ for an authenticated route (/page/home, /app/new-tnc, or another /app/… page).

Where hardening would pay, in order

  1. Get OTP disabled when empty (Group 4, test 3). One line: expect(disabled).toBe(true) — definite behaviour, no backend needed, already measured.
  2. Console errors (Group 10, test 1). Two lines, copied verbatim from PublicPage.spec.ts. Turns a buried log line into a build signal.
  3. Eye icon toggle (Group 5, test 3). Assert the type flips password → text, using the typed locator rather than input.nth(1).
  4. OTP mode selected by default (Group 3, test 1). Read the radio's checked state so the test matches its own name.
  5. Empty and whitespace rows in the edge-case loop. Assert those two; leave the other eight as observation.

The navigation tests are best left alone. Asserting destinations on a live shared environment would fail this suite for reasons that are not login-page defects — precisely the trade login-check.spec.ts exists to take, with credentials it owns.

15   Failure modes and fixes

SymptomMost likely causeWhat to do
All 29 tests fail The page never loaded, or Playwright was run from the repo root instead of SphereWebAutomation\. Check the URL printed by beforeEach. Run --grep "Page Health" — a failing title test confirms the page itself is wrong.
All five Password Login Flow tests fail with the same error The group's beforeEach could not click "Login with Password" — one cause, five reds. Check whether Group 3 also failed. Green Group 3 plus red Group 5 hook means the toggle works but the password screen does not render.
All four Help Modal tests fail together Same shape — the Group 7 hook could not open the modal. Check Group 1 test 3, which opens the modal independently. If that is also red, the Help control moved; fix helpControl() at line 26 and both groups recover.
"Cannot fill element" on the identifier field Something resolved to the OTP/Password radio — the first <input> on the page. Use identifierInput(page). This is the exact bug the helper at line 19 was written to prevent.
"Chat with us" test fails on a visible button The locator resolved to the hidden third-party chat widget whose text also contains that phrase. Keep .filter({ visible: true }) and the anchored /^chat with us$/i. Both constraints are load-bearing.
Back arrow test asserts the wrong button The .or(getByRole('button').first()) fallback engaged because the Material ligature text changed. Check the icon's rendered text in the DOM and add it to the /chevron_left|arrow_back/i alternation rather than relying on the positional fallback.
Every text assertion fails, page looks fine The environment is serving this page in Hindi. This file has no bilingual matching. Port the tr() helper and HI map from PublicPage.spec.ts and route the text matchers through it.
Login logs "Invalid username or password" The hard-coded testcase003@yopmail.com no longer exists on the target environment. Not a test failure — the suite stays green. Mint a fresh account (npm run mint:fresh-user) and update the literal, or move the credentials to env vars.
Flaky first assertion in a test The Angular shell had not finished painting when the assertion ran. beforeEach already waits for networkidle. If a specific control is still racing, give that one assertion an explicit timeout rather than adding a blanket waitForTimeout.
A --grep runs far more tests than expected You grepped the outer describe name, which is identical in PublicPage.spec.ts. Grep an inner group name, or pass the file path explicitly.
The one rule to keep This file's locators encode hard-won knowledge about a page whose controls are not what they look like — the first input is a radio, Help is not a button, the back arrow is icon ligature text, and a hidden widget shadows the chat button. Reuse the helpers rather than re-deriving the locators, and when you add a check, decide deliberately whether it asserts or observes. Both are legitimate here; what is not legitimate is a test whose name promises more than its body delivers.
