1   What this script does

It is the sweep of the learner's own profile page — the one screen where a user changes something about themselves rather than about a course.

/app/profile-view carries five left-nav sections, each with its own form, plus a profile panel, a header, and a logout flow. This spec puts 68 granular tests across all of it in ten groups, so a failure names the control rather than the page.

The five sections, and what each holds

SectionFields
Personal DetailsFirst and last name, phone, email (masked), date of birth as three dropdowns, country, pincode, Save
Organization DetailsBackground, designation, RN/RM number, organisation type, organisation name, Save
Academic DetailsAn Education block with an + Add Education control
Language PreferenceEnglish / हिंदी radios, and Save
My CertificatesThe certificate list, or its empty state

Around them: the profile avatar and its pencil edit icon, a Help and Support button, a Logout button that opens a confirmation modal, and the shared app header.

What makes this page harder to test than it looks

It is bilingual, and it can change
  • Every label renders in English or Hindi
  • One of this file's own tests flips the language
  • So English-only selectors break the tests that follow
  • Section 2 is entirely about this
It cannot be navigated to
  • A direct URL renders the Account route blank
  • So does a plain page.reload()
  • Every entry goes Home → header click
  • Section 3 covers the machinery
It writes to a shared account
  • Phone, pincode and organisation name are saved
  • The language is switched and switched back
  • Fields are read-only on production
  • So the mutating tests guard before they type

The file header promises independence, and the code mostly delivers "Each test is INDEPENDENT — reuses .auth-state.json from previous tests." There is no describe.serial anywhere, and a beforeEach resets the viewport, dismisses any leftover modal and re-opens the Account page if a previous test navigated away. What the tests do share is a single browser tab and a single real account — so independence holds for ordering, not for state. Section 3 covers the difference.

2   The bilingual engine

Every text assertion in this file matches English or Hindi. That is not future-proofing — it is a direct consequence of one of its own tests.

The Language Preference group switches the account to Hindi, saves, and checks the choice survives a reload. From that moment the entire UI is in Hindi, including the left-nav labels every later section needs to click. An English-only selector would not fail with a useful message; it would simply find nothing, and the rest of the run would collapse for a reason that had nothing to do with the page being broken.

3   Getting to the page, and staying there

The Account route does not render on direct navigation. Everything about this file's setup follows from that one fact.

Figure 2 — (A) the only navigation that works, and (B) the shared-tab lifecycle built around it.

Why openAccountViaHeader() retries

Three attempts, and each one re-does the whole hop rather than retrying just the click. Two details are worth calling out:

ChoiceReason
domcontentloaded, never networkidle The comment is emphatic and correct: this SPA never goes idle — long-polling and analytics keep the network busy, so networkidle would simply time out on a perfectly healthy page.
Clicking is not enough After the click it waits for accountMountedMarker() — the Position label or the Personal Details nav item, whichever appears — with an 8-second window. A click that navigates but leaves the panel unmounted counts as a failed attempt.

The header control itself is matched three ways (line 98): button, then link, then plain text. The source explains why — it renders as a <button> on this SPA, not a link, and it sometimes lags behind first paint, which is also why it gets a generous 12-second visibility window.

One helper name carries the whole lesson reNavigateToAccount() (line 191) is a one-line wrapper around openAccountViaHeader(), and it exists purely so that reload-then-verify tests read correctly. Its comment says: "Use this instead of page.reload(), which makes the Account route render blank." Naming the wrapper after the intention — re-navigate — rather than the mechanism is what stops the next person reaching for reload() and spending an afternoon on a blank page.
Shared tab, shared account, independent order Because there is one tab and one real learner, tests are not isolated from each other's effects — the language test changes what later tests see, and the save tests change stored data. What beforeEach buys is that the order does not matter and one failure does not cascade: each test starts on a mounted Account page at a known viewport with no modal open, whatever the last one did.

The guards on test 10 are the right instinct

On production the phone field is read-only — it is verified and masked — so a blind fill() would throw for a reason that is not a defect. The test checks isEditable() first, and does the same for pincode. Then it checks isEnabled() on Save, because the button stays disabled until an editable field actually changes: if nothing was editable, a disabled Save is correct behaviour, not a bug.

And when it cannot save, it says so honestly rather than pretending:

ℹ️  Save button is disabled (no editable fields changed) — nothing to save
Test 11 is named for the one thing it does not do "Saved values persist after page reload" re-navigates, re-reads the phone and pincode fields, and prints them. It never compares them to '9876543210' and '560001' — the values test 10 typed. A save that silently failed, or a backend that dropped the write, produces exactly the same green result.

The fix is two lines and needs no new machinery: have test 10 record what it actually filled (it already knows, because it guards on isEditable()), and have test 11 assert against that. As written, the two most valuable tests in the group — write it, then prove it stuck — prove nothing between them. The identical problem exists in Organization Details, Section 6.

Every test re-opens the modal

Tests 2, 3 and 4 each begin by clicking Logout again, because the file's beforeEach dismisses any leftover overlay — so each test starts from a clean page and has to reopen what it wants to inspect. That is four clicks on a Logout button in one run, and it is why the overlay-dismissal loop in beforeEach matters: without it, the second test's click would land on the first test's backdrop.

Test 4 measures the two things that matter most, and asserts neither After clicking No it gathers three signals: the URL (asserted), whether the modal is gone, and whether the profile marker is still visible. The last two are printed: 
✅ Modal closed (logout now text hidden): true
✅ User still authenticated (profile marker visible): true
The source is candid about the consequence — "a No that silently logged the user out would still be reported as a pass" — because the URL would remain on the profile route for a moment even after the session was dropped. Two expect() calls on values the test already computes would make this the strongest test in the file rather than the most nearly-strong one.

Taken together the group is still the best-shaped in the spec: 4 of 4 assert, the assertions are about behaviour rather than presence, and each names a genuine failure a user would notice. The gap in test 4 is narrow and one line wide.

Test 7 cannot see the errors it is named for "No console errors on Account page load" attaches its page.on('console') listener after the page has already loaded — beforeEach navigated to Account before the test body ran. The listener can therefore only catch errors that fire from that moment on. Load-time errors, which are the ones the title is about, have already happened and are gone.

The source is honest about it in a NOTE comment, which is better than hiding it, but the test name is not. And it has no expect() either: it counts, prints the first five truncated, and passes. Test 12 is wrapped, and for a good reason Creating an isolated context is the whole point of the unauthenticated test, but a CDP-attached browser cannot always create one — you are driving someone's real Chrome, not a fresh instance. The test wraps the creation and calls test.skip() with a message naming that reason — skipping honestly rather than passing for the wrong reason. In CI, where storageState mode gives it a proper isolated browser, the real check runs.

10   What green actually proves

Forty of the sixty-eight tests assert. The twenty-eight that do not are concentrated, not scattered — and that is the useful part.

Figure 3 — where the assertions are. The two ends of the file are strong; the middle is where a regression would go unnoticed.

Green means this, for certain
  • The Account page mounts, reached the only way that works
  • All five left-nav items render, in either language
  • Personal Details' fields and Save button are present
  • Both Save buttons render
  • Language options render and are labelled
  • Logout asks first, and offers both Yes and No
  • Cancelling does not navigate away
  • The page survives three viewports
  • A logged-out visitor cannot see the profile
Green does not mean this
  • That anything saved actually persisted — both persistence tests only print
  • That the email is masked
  • That a designation dropdown exists — only that a dropdown does
  • That any nav item is highlighted when selected
  • That the pencil opens an uploader
  • That Help and Support does anything
  • That the certificates list is correct
  • That the page loads without console errors
  • That cancelling logout keeps the session alive

Failure modes

SymptomCauseFix
Every test fails at once, with "Account page failed to mount" beforeAll's assertion. The header's Account control never appeared, across three attempts. The message names the likely cause: is TEST_USER logged in on the environment BASE_URL points at? Check both together — a valid session on the wrong environment looks identical.
A run goes red from the Language Preference group onwards The account is in Hindi and something is matching English only. Any new assertion must go through T or NAV_HINDI. If the run was interrupted mid-group, ensureEnglish() may not have fired — run that group alone once to reset the account.
Clicks land on nothing, several tests in a row A leftover modal backdrop. The Logout modal and the picture uploader both leave one. The beforeEach loop should have cleared it. If a new overlay shape has appeared, add it to the three-selector list at line 247.
The Account panel renders blank Something reached the route by URL or by reload(). Use reNavigateToAccount(). This is the single most common mistake when adding a test to this file, and the reason that wrapper exists.
