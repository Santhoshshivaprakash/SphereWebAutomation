Sphere Web Automation — Project Guide

The full suite for the Sphere learning platform — with the star addition: a one-command runner that completes an entire named competency, on production or locally over CDP.

https://sphere.aastrika.org Layered: UI · API · Monitor TypeScript · POM Complete-Competency runner
What we built. CompleteCompetency.spec.ts — give a competency name in the terminal and it clears every level end to end. It answers with the real S3 answer key (fetched via the content hierarchy, no token), bypasses poisoned keys, and runs on production (password login) or locally over CDP (Chrome/Edge). Everything runs from direct terminal commands — no wrapper scripts.

⭐ Compare production vs staging (side by side)

scripts/compare-env.mjs loads every feature in config/compare-routes.json on both environments at the same time, in two browser contexts, and reports what differs — UI (screenshots left/right, pixel diff, missing headings/buttons/fields/links, broken images, copy drift), function (HTTP status, redirects, blank pages, console + uncaught JS errors, failing requests, settle time, build hash) and data (API parity, and which courses exist on one environment but not the other). Output: a branded side-by-side HTML report + JSON summary in compare-reports/. It exits 1 when anything blocking is found, so it can gate a release.

# ⭐ the usual one — signed in on both sides, everything, opens the report
npm run compare:all

# interactive picker: which two envs → signed in or public → which features → options
npm run compare

# any flag skips the prompts entirely
npm run compare -- --auth              # same as compare:all, without --open
npm run compare -- --headed            # public pages only, watch it run
npm run compare:journeys               # create-account · login · profile-tabs, step by step
npm run compare:signup                 # just the create-account journey
npm run compare:local                  # production vs http://localhost:3000

# scoping and tuning
npm run compare -- --auth --only competency,my-courses   # match route id or name
npm run compare -- --auth --route /app/profile-view      # a one-off path
npm run compare -- --auth --threshold 1.5                # ignore visual diffs under 1.5%
npm run compare -- --auth --no-catalogue                 # skip catalogue parity (faster)
npm run compare -- --auth --refresh                      # re-login + re-fetch the catalogue
npm run compare -- --auth --a https://sphere.aastrika.org --b https://portal-staging.aastrika.org

The defaults are already --a https://sphere.aastrika.org and --b https://portal-staging.aastrika.org, so prod vs staging needs no URLs. Credentials for --auth, most specific first: PROD_EMAIL/PROD_PASSWORD · STAGING_EMAIL/STAGING_PASSWORD → TEST_USER_EMAIL/TEST_USER_PASSWORD → MONITOR_* → config/accounts.json.

05CompleteCompetency.spec.ts — the runner

Give a competency name; it clears every level. How it answers, in order:

  • Real S3 answer key — from the viewer URL it reads the level + course ids, fetches the content hierarchy (org/rootOrg headers only — no expiring token), finds the level's S3 quiz artifact, and matches each on-screen question to the pool to pick the correct option by text.
  • Poisoned-key bypass — the app serves a stripped quiz (isCorrect:false); the runner ignores it and uses the real S3 key instead.
  • Per-page answering — one question per page: scrape → match → select → Next/Submit, until the result screen.
  • Gemini fallback — only if the real key is genuinely unavailable; with 429 backoff.
Env varPurpose
COMPETENCY_NAMECompetency to complete (required)
BASE_URLReal env for password login (prod/staging); or localhost with USE_CDP=1
USE_CDP1 → attach to the logged-in browser on :9222 (local)
COMPETENCY_USER_EMAIL / _PASSWORDOverride the forced standard account
GEMINI_API_KEYAI fallback (optional)
Standard account: sphereid041@yopmail.com / Sunbird@123 (forced for this flow on production).

06Run locally over CDP

Password login doesn't work on the localhost mirror, so attach to a browser you're already logged into. Two steps:

1 — launch a CDP browser on :9222, then log in

# Edge (clean profile, extensions disabled)
& "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" --remote-debugging-port=9222 --user-data-dir="$env:TEMP\sphere-cdp-edge" --disable-extensions --no-first-run http://localhost:3000

# or Chrome
& "C:\Program Files\Google\Chrome\Application\chrome.exe" --remote-debugging-port=9222 --user-data-dir="$env:TEMP\sphere-cdp" --no-first-run http://localhost:3000

In the window that opens, sign in at http://localhost:3000 and leave it open. The profile persists, so you log in once.

2 — run the competency against it

$env:USE_CDP="1"; $env:BASE_URL="http://localhost:3000"; $env:COMPETENCY_NAME="Care of the newborn"; npx playwright test tests/CompleteCompetency.spec.ts --headed
Account note. In -Local (CDP) mode the account is whoever is signed into that browser — not necessarily sphereid041. The standard credentials apply only to the production path.

The runner reuses your logged-in tab (Sphere keeps its session in per-tab sessionStorage, so a fresh tab would look logged-out).

08Reporting

Reporters run on every test run (configured in playwright.config.ts):

  • Branded HTML — reporters/brand-html-reporter.ts → brand-reports/
  • Excel — reporters/excel-reporter.ts → test-reports/excel-reports/

npm run report                # open the last Playwright HTML report

09Roadmap — to a production-grade platform

Reliability

  • Replace fixed waitForTimeout calls with web-first assertions / expect.poll.
  • Keep retries low but add trace: 'on-first-retry' everywhere; video/screenshot on failure.
  • Centralize selectors; add data-testids where the app allows.

Auth & local runs

  • Document the CDP flow in README; auto-detect a running :9222 before launching a new one.
  • Optionally support headless prod runs for the competency runner in CI.

Coverage & engineering

  • ESLint + Prettier + tsc --noEmit gate; TypeScript strict.
  • Tag suites (@smoke, @competency, @auth) for selective CI runs.
  • Cross-browser (Chromium + WebKit) for read-only flows.

Regression on every release — .github/workflows/regression.yml (already in the repo)

This workflow runs the full regression after every published release (and via a manual “Run workflow” button). It's committed at .github/workflows/regression.yml:

name: regression
on:
  release:
    types: [published]     # fires after every GitHub Release
  workflow_dispatch: {}     # manual run button
jobs:
  regression:
    runs-on: ubuntu-latest
    timeout-minutes: 60
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npm run test:regression
        env:
          BASE_URL: https://sphere.aastrika.org
          HEADLESS: 'true'
          TEST_USER_EMAIL: ${{ secrets.TEST_USER_EMAIL }}
          TEST_USER_PASSWORD: ${{ secrets.TEST_USER_PASSWORD }}
          GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: regression-reports-${{ github.run_number }}
          path: |
            brand-reports/
            playwright-report/
            test-reports/

Store TEST_USER_EMAIL, TEST_USER_PASSWORD, GEMINI_API_KEY (and the SMTP_* / ALERT_EMAIL_* keys to email the report) as GitHub Actions secrets. Enable branch protection on main. The report is uploaded as a run artifact. How it triggers: publish a Release in GitHub → the regression runs automatically.
