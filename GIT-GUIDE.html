Git for SphereWebAutomation

What git is doing here, in plain English — and exactly what to run when a new build lands on staging.

1. What git is for in this project

Git keeps a history of the test code you write. It does not keep your test results or your passwords. That split is the single most important idea here:

Goes into gitNever goes into git
tests/ — the specs
scripts/ — the runners
config/ — routes, accounts list
package.json, playwright.config.ts 		.env secrets
test-reports/, brand-reports/
compare-reports/, test-results/
.auth/ (saved logins), node_modules/
Why reports are excluded. They are produced fresh by every run and would bloat the history within days. Share the HTML or PDF report by attaching it to an email or chat, not by committing it.

Why .env is excluded. It holds real passwords and API tokens. It is listed in .gitignore, so git will not offer to commit it even if you forget. If you add a new variable, tell the team what to add — do not push the file.

The four places your work lives

your folder ──git add──▶ staging area ──git commit──▶ your history ──git push──▶ GitHub
 (edits)                    (chosen changes)         (saved forever)       (shared)

GitHub ──git pull──▶ your folder   (what other people pushed)

This project has one branch, main, and one remote called origin: github.com/Santhoshshivaprakash/SphereWebAutomation.

2. A new build is deployed to staging — what do I do?

Staging is https://portal-staging.aastrika.org. Nothing about a deployment changes your code automatically — you pull the latest tests, run them against staging, and then deal with whatever fails.

1

Get the latest test code

Someone may have fixed a selector or added a spec since you last ran. Start clean.

# go to the project (git only works inside it)
cd D:\Automation\SphereWebAutomation

# is anything half-finished from last time?
git status

# bring in everyone else's work
git pull

git status should say nothing to commit, working tree clean. If it lists files, see §4.

2

Install anything new (only if dependencies changed)

# safe to run any time; required if package.json changed in the pull
npm install
3

Run the tests against staging

The saved scripts point at production. For staging you set BASE_URL first.

# point this terminal at staging (stays set until you close it)
$env:BASE_URL="https://portal-staging.aastrika.org"

# the interactive runner — asks which environment and which spec
npm run go

# or the whole UI suite
npm run test:ui

# or one spec
npx playwright test tests/PublicPage.spec.ts --project=Chrome --headed
4

Read the result and decide which kind of failure it is

What happenedWhat it meansWhat to do
Test fails, app is fineThe build changed a label, id or flow — the test is out of dateFix the test code, commit, push (step 5)
Test fails, app is brokenA real defect in the new buildRaise the bug with the report attached. Do not change the test to make it pass
Login failsUsually a wrong or missing credential for that environmentFix .env locally — nothing to commit, it is not tracked
5

Save and share your fix

# what did I change?
git status
git diff

# stage the files you actually want (not everything blindly)
git add tests/CourseComplete.spec.ts

# save it with a message that says WHY, not just what
git commit -m "Fix course search after staging build changed the placeholder"

# send it to GitHub for the team
git push
Working straight on main is fine for small fixes because this repo has one author. For anything larger, branch first — see §3.

3. Using a branch (for bigger changes)

A branch is a side copy where you can experiment without disturbing main.

# create a branch and switch to it
git checkout -b fix/staging-login

# ...edit, run, repeat...
git add .
git commit -m "Verify the session before saving it"

# push the branch the first time
git push -u origin fix/staging-login

# when it works, bring it back into main
git checkout main
git pull
git merge fix/staging-login
git push

4. Common situations

"git status shows files I did not mean to change"

# throw away changes to one file
git restore tests/SomeSpec.spec.ts

# put everything aside temporarily (get it back with: git stash pop)
git stash

"git pull says there is a conflict"

You and someone else changed the same lines. Git marks them in the file like this:

<<<<<<< HEAD
your version
=======
their version
>>>>>>> origin/main

Open the file, keep the correct lines, delete the <<< === >>> markers, then:

git add <the file>
git commit

"I want to see what changed recently"

git log --oneline -10                    # last 10 commits
git log --oneline -- tests/Account.spec.ts   # history of one file
git show 71d57f6                         # what a commit contained
Two things to never do. Do not commit .env (it is ignored — keep it that way), and do not use git push --force on main. Force-pushing rewrites shared history and can delete someone else's work.

6. The short version

  1. git pull — start from the latest tests.
  2. Set BASE_URL to staging, run the suite.
  3. App broken → raise a bug. Test outdated → fix the test.
  4. git add → git commit -m "..." → git push.
  5. Reports and .env stay on your machine — git already ignores them.
