1   What this script does

It is the first suite in the set that runs inside the product — the page a logged-in learner lands on to pick up where they left off.

/app/user/my_courses is the learner's home base. It carries three tabs: Started (courses in progress, each with a progress bar and a Resume button), For You (a recommended grid), and Completed (which is empty for a new account). This spec walks all three, plus the shared header and a set of page-health checks.

Because the page is behind a login, the suite cannot just navigate to a URL — it needs an authenticated session first. Section 2 covers how it gets one, and the unusual browser-tab arrangement that follows from it.

The file's header promises that "each test is INDEPENDENT — a failure in one doesn't block the others", and that holds: there is no describe.serial anywhere, and every test re-navigates through beforeEach. What the tests share is a browser tab, not state.

The four things it covers

Tab structure
  • All three tab labels render with a (n) count
  • Counts are non-negative integers
  • Switching tabs changes the content
  • The URL stays on /my_courses throughout
Tab contents
  • Started: thumbnails, titles, progress, Resume
  • For You: card grid, badges, ratings, providers
  • Completed: the empty-state message
  • Clicking through to a course
Shell and health
  • Logo, search bar, Home link, bell, dark mode
  • Renders at 390, 768 and 1440px
  • Title, reload persistence, console errors
  • Unauthenticated access redirects to login
Its content assertions depend on a real account's real data Several tests look for specific course titles (Hypertension in Pregnancy, Normal Labour) and providers (Jhpiego, Indian Nursing Council) that exist only if the logged-in account has those courses. The script handles this by counting how many of a known list it found and printing the tally rather than requiring any of them — which is why so much of the suite observes rather than asserts. Section 4 explains the trade; Section 12 measures it.

2   Authentication and the shared tab

Two architectural decisions shape this file: where the session comes from, and the fact that all 49 tests share one browser tab.

Figure 1 — Authentication is resolved once per worker from whichever env mode is set; the page fixture is then overridden so all 49 tests share a single tab, with beforeEach resetting viewport and URL to undo any leakage.

The fixture override, in full

// :23 — extend the authenticated base test with a shared page
const test = authedBase.extend<{}>({
  page: async ({ context }, use) => {
    if (!sharedPage || sharedPage.isClosed()) {
      sharedPage = await context.newPage();      // created on first use only
    }
    await use(sharedPage);
    // Do NOT close between tests — keep the single tab open.
  },
});

test.afterAll(async () => {
  await sharedPage?.close().catch(() => {});    // closed exactly once
  sharedPage = undefined;
});

The isClosed() guard matters: if something closes the tab mid-run, the next test transparently opens a new one rather than failing on a dead handle.

Why this is safe, and when it would stop being The file's own comment gives the reasoning: workers=1 plus fullyParallel=false means tests already run sequentially, so there is never a second test wanting the tab at the same time. Turn on parallelism and this override breaks immediately — two tests would drive the same tab at once. The shared tab is a deliberate optimisation bought with a config guarantee, not a free one.

4   Two kinds of test

18 of the 49 tests assert. The other 31 measure something and print it. Both shapes appear throughout the file, and telling them apart is the key to reading a run.

Figure 3 — The two shapes, and the conditional pattern that gets real coverage out of data-dependent content. That pattern appears once in the file; Section 13 lists where else it would apply.

The ✅ in the logs does not mean "passed" Almost every test in this file prints a line beginning ✅, including the observing ones — and an observing test prints its checkmark whether the value it measured was true or false. When reading a run, read the value after the colon, not the tick before it.

The -1 sentinel in test 7 is doing real work

const match = txt?.match(/\((\d+)\)/);
const count = match ? parseInt(match[1]) : -1;   // unparseable → -1
expect(count).toBeGreaterThanOrEqual(0);          // so -1 FAILS

Defaulting to 0 instead would have made a missing or malformed count pass silently — the test would assert "0 ≥ 0" and report green on a tab whose label had lost its number entirely. Choosing -1 turns the absent case into a failure. It is a small decision that determines whether the test is real.

Comparing the vertical positions of the first three cards, with a 20px tolerance for card-height variation, proves the grid is three-wide at desktop width without hard-coding any CSS. It is the only layout check in the suite that inspects geometry rather than visibility — and the result is printed, not asserted. Column count at 1440px is fixed design, not account data, so expect(sameRow).toBe(true) would be safe.

Why this group has no assertions — and what could be asserted anyway Every element here belongs to a card, and whether any cards exist depends on what the recommendation engine returns for this account. That justifies the caution. But three things in the group are not account-dependent: the 3-column layout (test 10), the tab-count-versus-cards relationship (test 9), and the conditional "if cards exist, each must have a thumbnail" (test 3). All three could take Group 2's if (count > 0) shape and become real coverage without becoming fragile.
A locator worth tightening Test 5's text=/\d\.\d/ matches any decimal anywhere on the page — a duration, a price, a version string. On a card grid it almost certainly resolves to a rating, but the locator does not say so. Scoping it to a card would make it mean what its title claims.

The comment in test 2 is the right call — and it points at a better assertion

Refusing to assert count === 0 is correct: the suite may run as an account that has genuinely completed something, and failing on that would be wrong. But the group then extends that caution to tests 5 and 6, where it need not apply. Those two are about internal consistency, and consistency is assertable whatever the count is:

// what tests 5 and 6 measure today — printed only
console.log(`✅ Card count in empty Completed tab: ${count}`);
console.log(`✅ Resume buttons in Completed tab: ${count}`);

// what they could assert, using the count they already read in test 2
if (completedCount === 0) {
  expect(cardCount).toBe(0);      // empty tab ⇒ no cards
  expect(resumeCount).toBe(0);    // Resume belongs to Started, never here
}

A Resume button appearing in the Completed tab would be a real defect — it offers to resume a course the learner has finished — and today the suite would print the number and pass.

Test 4's title and its code disagree The test is called "Empty-state message text matches exactly" but passes { exact: false } and then logs the text rather than comparing it. What it actually does is a substring search. The empty-state copy is fixed product text, so an exact comparison is entirely safe — this is one of the cleanest one-line fixes in the file.

Test 1's whole-body comparison

const startedHTML = await page.locator('body').innerHTML();
await clickTab(page, 'For You');
const forYouHTML  = await page.locator('body').innerHTML();
expect(startedHTML).not.toEqual(forYouHTML);

Comparing the entire body is deliberately blunt, and that is its strength: it needs no knowledge of what either tab contains, so it works for any account with any data. If clicking "For You" silently failed — a dead tab, a JavaScript error swallowed by the framework — the two snapshots would be identical and the test would fail.

The weakness is the mirror image. Anything that changes between the two captures satisfies it: a re-rendered timestamp, a rotating banner, a lazily-loaded image that arrived in between. It proves something changed, not that the right thing changed. For a tab-switch smoke check that is a reasonable trade, and it is the only tool available that does not depend on the account's data.

Tests 2 and 3 are the assertable ones that are not asserted Both describe deterministic product behaviour. Test 2 gathers beforeEmpty and afterEmpty — the exact pair needed to state "the empty-state message was not on For You and is on Completed" — and prints them. Test 3 reads whether Started's content came back and prints that. Neither depends on how much data the account has, only on whether the tab panel re-rendered, so both could assert. Test 2's assertion would need guarding on the Completed count being zero; test 3's on there being started courses at all — the if (count > 0) shape from Group 2 again.

Eight other tests across the suite click something and log the resulting URL. This one compares it:

await scrollAndClick(page, homeLink);

The alternation is the reason it can assert safely — Sphere serves the authenticated home under both /app/home and /page/home depending on the build, and accepting either means the test checks "we reached home" without pinning a routing detail. Test 5's six-way locator is a sign of an unstable control Six alternatives, an explicit 5 s timeout, and an observe-only result together say the dark-mode toggle has moved more than once and is not reliably findable. That is honest — but it also means the test cannot tell "the toggle moved again" from "the toggle was removed". Since it only reports, the practical effect is that a vanished toggle shows up as one false in a wall of logs.

Test 7 — the most valuable test in the file

// :531 — note the fixture: { browser }, NOT { page }
const context = await browser.newContext({ storageState: undefined });  // no session
const page = await context.newPage();
await page.goto(MY_COURSES_URL);
expect(page.url()).toMatch(/login|public/i);
await context.close();

Three things make it stand out. It takes { browser } instead of { page }, deliberately opting out of the shared authenticated tab. It passes storageState: undefined to guarantee a sessionless context — inheriting the worker's state would make it pass for the wrong reason. And it closes its own context afterwards.

What it verifies is access control: a logged-out visitor typing the My Courses URL must be bounced to a public route. Everything else in this suite checks presentation; this checks the page is actually protected.

Test 1 is one line from being real It captures console errors, counts them, prints up to five — and asserts nothing. The sibling PublicPage.spec.ts runs the same check and does assert, after filtering resource-load noise. The same two lines work here: 
const jsErrors = errors.filter((e) => !/Failed to load resource/i.test(e));
expect(jsErrors).toEqual([]);
An authenticated page is exactly where an uncaught exception matters most — a broken render here strands a learner mid-course.

How to read a run

The 31 observing tests emit a structured snapshot of what the page showed — but the information lives in the values, not the pass count. Scan the log for false and for zero tallies:

✅ Started tab visible rows: 5
✅ First course thumbnail visible: true
   ✓ Title: "Initial assessment protocols for ANC"
✅ 1/5 known titles visible in Started
✅ Progress bar visible: false        ← 5 rows, but no progress bar found
✅ Progress percent text: "(none)"    ← and no percentage either
✅ Resume buttons visible: 5 (started rows: 5)

Every line above is green. Together they describe five course rows with Resume buttons intact and the progress indicator missing — a real regression, reported as a pass.

The suite's honest value Treat this file as two things at once: a small, reliable gate on page structure and access control, and a much larger instrument that photographs the page's contents each run. The first protects the build; the second is only useful to someone who reads it.

  • 4.6 Resume never belongs in Completed
Needs a guard — depends on data
  • 2.9 / 3.9 Guard on count > 0 — a paginated or lazily-loaded list may show fewer rows than the tab declares
  • 4.5 / 5.2 Guard on the Completed count being zero
Two caveats before changing 2.9 and 3.9 These two look like the most obvious fixes and are the least certain. The tab label's count comes from the API; the visible row count comes from the DOM. They can differ legitimately — if the list virtualises, paginates, or lazy-loads on scroll, fewer rows are in the DOM than the count declares, and a strict equality assertion would fail on a working page. Before asserting equality, confirm the list renders every item at once. If it does not, the honest assertion is expect(visibleCount).toBeLessThanOrEqual(declaredCount) plus toBeGreaterThan(0) when the declared count is non-zero.
A cheaper fix than changing the assertions If these stay as observations, rename them so a report does not overstate what happened — "Log Started tab count vs visible rows" rather than "… matches …". Only the titles mislead.

15   Failure modes and fixes

SymptomMost likely causeWhat to do
The run aborts before any test with a credentials error No auth mode is configured — authedTest throws rather than running against a login page. Set one of the four modes from Section 2. The thrown message lists them. This is the intended behaviour, not a bug.
Every test fails with "element not found" and the URL is /public/login The session expired or was rejected — the suite is being redirected to login on every navigation. Delete .auth/state.json and re-run so the session is re-established. If mode 1, confirm the CDP Chrome is still logged in.
Tab-specific groups all fail in their hook clickTab could not find the tab — one cause, nine or ten reds in that group. Check Group 1 first. If the tab labels assert fine there, the markup for the clickable tab changed; extend the five-way selector list at line 50.
A test fails at an unexpected viewport A previous Group 7 test left the shared tab at 390px and something bypassed the reset. beforeEach resets to 1280×800 — confirm it ran. This is the specific hazard the shared-tab design creates; see Figure 1.
Group 3's grid test logs "Only 2 cards — skipping" The recommendation engine returned fewer than three cards for this account. Expected on a sparse account. Run as an established user if you want the grid geometry actually measured.
All the title and provider tallies read 0/5 or 0/4 The account is not enrolled in any of the hard-coded courses, or the catalogue changed. Not a failure — the tests pass. Update the known-title lists at lines 155 and 277 to match the catalogue you actually test against.
"Started vs For You content differs" fails The tab click did nothing — the two body.innerHTML snapshots came back identical. A real finding. Confirm with Group 5 test 4, which checks the URL across all three switches.
The unauthenticated-redirect test fails The page served itself to a sessionless context — a genuine access-control problem. Treat as an incident, not a test issue. The test builds its own clean context with storageState: undefined, so it cannot fail from session leakage.
A test fails on a dead page handle Something closed the shared tab mid-run. The fixture's isClosed() guard should reopen it transparently. If it recurs, look for a navigation that kills the context — a popup or a hard redirect.
Two tests interfere with each other Parallelism was enabled, breaking the shared-tab assumption. This file requires workers=1 and fullyParallel=false. Either restore them or remove the page-fixture override.
The one rule to keep This page renders one account's real data, so most of its content cannot be asserted absolutely — but almost all of it can be asserted conditionally. The Resume test at line 181 shows the shape: measure the precondition, then require the relationship. When you add a test here, take that shape rather than defaulting to a console.log, and make sure the test's name describes what its body actually does.
