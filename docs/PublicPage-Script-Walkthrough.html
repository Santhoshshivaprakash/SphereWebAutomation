1   What this script does

It is the shop-window check: everything a visitor sees before they have an account, verified element by element, in whichever language the portal happens to be serving.

The public home page at /public/home is the only page most first-time visitors ever see. It carries the value proposition, the live platform statistics, the course carousels, the partner credibility block, the explainer videos and the entire footer — and every one of those is a separate conversion risk if it breaks. This spec walks the page top to bottom and checks each element individually.

It needs no login, creates nothing, and changes no server state. That makes it the cheapest suite in the project to run and the safest to run often.

The four things it verifies

Presence
  • Logo, headings, subtexts
  • The four platform statistics with their exact numbers
  • Section headings down the whole page
  • Footer columns and copyright
Navigation
  • Log in opens a modal, Escape closes it
  • Create Account and Start Today navigate
  • Both View All links navigate
  • Course cards, Privacy policy, Terms of Use
Integrity
  • No broken images anywhere on the page
  • No JavaScript console errors
  • Page loads in under 10 seconds
  • Page title names Sphere or Aastrika

Bilingual by design

This is the defining constraint of the suite. sphere.aastrika.org serves the public page in Hindi by default, but the same build can render English. A suite written against English strings would fail wholesale on the live site; one written against Hindi would fail on a rebuilt English environment.

So every text assertion in the file goes through one helper, tr(), which matches either language. Section 3 explains how it works. Labels that render identically in both languages — course titles, partner names, numbers, email addresses — are matched directly.

2.1   How the target URL is built

The spec takes an origin and appends the path itself, defending against two ways the environment variable is commonly mis-set:

// tests/PublicPage.spec.ts:16
const BASE_URL = (process.env.BASE_URL ?? 'https://sphere.aastrika.org')
  .replace(/\/+$/, '')               // strip trailing slashes
  .replace(/\/public\/home$/, '');   // strip an already-appended path

const PUBLIC_URL = `${BASE_URL}/public/home`;
BASE_URL as suppliedPUBLIC_URL that results
(unset)https://sphere.aastrika.org/public/home
https://sphere.aastrika.org/https://sphere.aastrika.org/public/home

Without the second replace, the third row would produce /public/home/public/home — a 404 that would fail all 64 tests with a misleading "element not found" on every one.

2.3   The two scroll helpers

HelperLineBehaviour
scrollAndClick:74 scrollIntoViewIfNeeded() then click(), both unguarded. Used where the element is expected to exist — a missing one should fail loudly.
safeScroll:81 Scrolls with a 3 s timeout, swallows the error, and returns whether the element is visible. Used for elements that legitimately vary between builds — partner logos, collaboration marks, social icons. Without it, one absent logo costs a 15 s scrollIntoViewIfNeeded timeout and a red test for something that was never guaranteed. 
// :81 — returns a boolean instead of throwing
async function safeScroll(locator): Promise<boolean> {
  await locator.scrollIntoViewIfNeeded({ timeout: 3000 }).catch(() => {});
  return locator.isVisible().catch(() => false);
}

safeScroll is the single mechanism behind most of the suite's soft tests. It is a deliberate trade — fewer false failures, at the cost of a green result that may have checked nothing. Section 17 lists exactly where that applies.

3   The bilingual engine

One helper, one lookup table, and every text assertion in the file becomes language-agnostic.

Figure 1 — tr() turns one English key into a regex that matches either language, so the same assertion is green on a Hindi build and an English one.

The whole helper, in six lines

// :66
function tr(en: string): RegExp {
  const esc  = (s: string) => s.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
  const alts = [en, ...(HI[en] || [])].map(esc);
  return new RegExp(alts.join('|'), 'i');
}

Why each of the three steps is load-bearing

  1. The English key always comes first in the alternation. That is what makes an unmapped label work — tr('Normal Labour & Birth') has no HI entry, so it degrades to a plain English match rather than throwing.
  2. Escaping is not optional. Real labels on this page contain &, +, ?, ! and . — "Help & Contact", "50+ Partner Organizations and Growing", "New User?", "Transform your Healthcare career through Sphere!". Unescaped, 50+ would mean "one or more zeroes" and would not match the text on screen.
  3. The i flag lets tr('TOP COURSES') match a heading the CSS may render in any case, and covers casing drift between builds.
Adding a label When a new string appears on the page, add one entry to the HI map at line 27 and use tr('Your English Label') in the test. Nothing else changes. If the label happens to render identically in both languages, skip the map entry entirely — tr() already handles that case.

4   The execution model

Unlike the signup suite, nothing here is serial. Every test starts from a clean page and is independent of every other.

Figure 2 — One beforeEach navigation per test, then one of four body shapes. The four patterns account for all 64 tests.

The trade this model buys Re-navigating for every test is slower than walking the page once, but it makes each test a standalone statement about one element. A failure names exactly one thing, no test can corrupt another's starting state, and --grep on any single test name reproduces the failure precisely. On a read-only page with no server cost, that is the right trade.

Test 4 is the template the others should follow

Course cards are lazy-loaded: the carousel populates from an API call that resolves after the scroll. An immediate count() is a single snapshot with no retry — call it a moment too early and it returns zero on a page that fills in correctly a second later. That is exactly how an intermittent failure is born.

// :264 — the comment in the file says it plainly
// Auto-wait for the (lazy-loaded) cards instead of an instantaneous count()
// that can fire before the carousel populates.
await expect(certBadges.first()).toBeVisible({ timeout: 15000 });
const count = await certBadges.count();
expect(count).toBeGreaterThan(0);

Tests 3 and 5 still use the bare count() form. They pass because test 4's pattern is not the only thing keeping them honest — the preceding scrollIntoViewIfNeeded gives the carousel time to fill — but they are the two most likely places in this group for an intermittent failure to appear. If either starts flaking, copy the toBeVisible-then-count shape from test 4.

Why ws-web-course-card comes first in the locator It is the Angular component's own tag name — the most stable handle available, because it changes only if the component itself is renamed. [class*="course-card"] follows as a fallback for builds where the markup differs. Ordering the specific selector first and the loose one second is the pattern used throughout this file.

The guarded shape, and what it costs

Tests 6 and 7 name real CNE course titles. Matching by exact string is stronger than "some card exists" — it proves the carousel serves accredited content rather than the general catalogue. Tests 8 and 9 check the accreditor badges, and all four share one shape:

const badge = page.getByText('Indian Nursing Council').first();
if (await badge.isVisible()) {          // ← absent? the body never runs
  await expect(badge).toBeVisible();      // ← can only ever pass
  console.log('✅ Indian Nursing Council badge visible');
}

Present, it asserts something true; absent, the test passes silently. The console line prints only on the success branch — so a run log without that checkmark is the real signal the element was missing. The same guard means a retired or renamed course stops being checked rather than failing.

Reading this group's result honestly A green CNE group guarantees three things: the heading renders, the carousel has at least one card, and View All works. Everything else — hours badges, arrow, the two named courses, both accreditor badges — is advisory. Read the console output, not just the pass count.

The text-or-image locator

Four of the five logo tests use the same two-way locator:

page.getByText('FERNANDEZ').or(page.locator('img[alt*="Fernandez"]')).first()

A partner mark may be rendered as an SVG with a text node, or as a raster image with alt text — and which one it is has changed between builds. Matching either means the test survives that change. The UNFPA test (6) matches only on image selectors, because that mark has no text form.

Why softness is defensible here and less so elsewhere Partner logos are a content list the business edits. A logo disappearing because a partnership ended is a content change, not a regression, and failing a build over it would train people to ignore the suite. Contrast this with the hero carousel in Group 2, where the content is fixed and only the timing is variable — there, softness papers over a real flake. Same mechanism, different justification.

Tests 3–5 are hybrids

Each makes two hard text assertions and then attempts one soft interaction. That is a useful shape: the part that is guaranteed — the card's copy — fails loudly, while the part that is fragile — a video player overlay — only logs. The play-button locator is shared across all three tests and indexed by position:

const playBtns = page.locator('[class*="play"], [aria-label*="play"], button[class*="video"]');
if (await playBtns.count() >= 2) {        // step 2 needs at least two to exist
  await playBtns.nth(1).click();          // index 1 = the second card's button
  await page.waitForTimeout(1000);
  await page.keyboard.press('Escape');      // dismiss whatever opened
}

The count guard is what makes positional indexing safe — nth(2) on a page with two buttons would otherwise throw rather than skip.

What the Escape press is really for Clicking play may open a modal video player. Because every test gets a fresh page, a stuck overlay could not leak into the next test anyway — but the Escape keeps the end-of-test screenshot (captured for every test, pass or fail) showing the page rather than a video frame. Small thing; it makes the report readable.

16   Group 14 — Page-wide checks

Page-Wide Checks  ·  4 tests  ·  line 760  ·  all four hard

What it proves: the page as a whole is healthy — no dead images, no JavaScript errors, acceptable load time, correct title. These are the four tests that look at the document rather than at one element, and every one of them can fail.

16.1   No broken images

The most carefully engineered test in the file, and the one worth understanding in detail. Two problems had to be solved: lazy-loaded images never start loading unless scrolled to, and an image mid-flight looks identical to a broken one.

  1. Scroll the entire page in 12 steps. window.scrollTo(0, i * innerHeight * 0.9) with a 400 ms pause each, so every loading="lazy" thumbnail enters the viewport and begins fetching. The 0.9 factor overlaps the steps slightly — nothing is skipped between them.
  2. Jump to the bottom with scrollTo(0, document.body.scrollHeight), catching any content the fixed steps missed on a longer-than-expected page.
  3. Wait for quiet — waitForLoadState('networkidle') (errors swallowed) plus a further 3000 ms, so in-flight image requests finish.
  4. Collect only genuine failures in the browser, using a three-part filter.
  5. Warn, then assert. Any broken URLs are logged with console.warn before expect(brokenImgs).toEqual([]) fails — so the report names the exact files.
Array.from(document.querySelectorAll('img'))
  .filter((img) => {
    const src = img.currentSrc || img.src;
    if (!src || src.startsWith('data:')) return false;  // skip inline data URIs
    return img.complete && img.naturalWidth === 0;        // FINISHED, but has no pixels
  })

The complete && naturalWidth === 0 pair is the whole trick. complete means the browser has finished trying; naturalWidth === 0 means it got nothing. Together they mean a real 404 or a decoding failure. An image still downloading reports complete: false and is ignored, as is a lazy image that never scrolled into view — so the test cannot fail on timing alone.

16.2   No console errors

Attaches a console listener, reloads the page, and collects everything of type error. It then filters the list before asserting:

const jsErrors = errors.filter((e) => !/Failed to load resource/i.test(e));
expect(jsErrors).toEqual([]);

Resource 404s are excluded deliberately — a missing analytics beacon or a third-party font would otherwise fail a page whose own code is fine, and broken images already have their own dedicated test above. What survives the filter is real JavaScript: uncaught exceptions, failed promise rejections, framework errors. Those fail the test, and are printed first with console.warn.

16.3   Page loads within 10 seconds

const start = Date.now();
await page.reload();
await page.waitForLoadState('domcontentloaded');
expect(Date.now() - start).toBeLessThan(10000);

The elapsed time is printed on every run, pass or fail, which makes this the file's de facto performance trend line — the number in the log is useful even when the test is green. Note the measurement stops at domcontentloaded, not at full load: it covers HTML and blocking scripts, not lazy images or carousel API calls. It is a "did the page get going" check, not a complete page-weight budget.

16.4   Page title

expect(await page.title()).toMatch(/sphere|aastrika/i);

Cheap, and a genuinely useful canary: a wrong or empty title usually means the router served the wrong shell, a deploy landed on the wrong environment, or an error page is being returned with a 200. The title is logged either way.

Run this group first when triaging If the whole suite is red, --grep "Page-Wide" answers "is the page fundamentally broken, or did one element move?" in four tests and about twenty seconds. A failing title or a flood of console errors explains the other sixty failures; all four green means the problem is a selector, not the page.

17   Hard vs soft: what green actually proves

22 of the 64 tests can pass without checking anything. Here is exactly which, so a green report can be read accurately.

A soft test is one whose assertion sits behind an if (await …isVisible()) or if (count >= n) guard. When the element is present it asserts something real; when it is absent the body never runs and the test reports green. A log test has no expect() at all. Neither is a defect — both are deliberate choices against flakiness — but both change what a pass means.

19   Failure modes and fixes

SymptomMost likely causeWhat to do
All 64 tests fail on "element not found" The page never loaded — usually a bad BASE_URL, or Playwright run from the repo root instead of SphereWebAutomation\. Run --grep "Page-Wide" first. A failing title test confirms the page itself is wrong; check the URL printed by beforeEach.
Every text assertion fails, but the page looks fine The portal is serving a language variant the HI map does not cover. Open the page, copy the actual rendered strings, and add them to the map at line 27. tr() accepts an array, so add a variant rather than replacing one.
One of the four stat tests fails Almost certainly not a bug — the platform's live counter moved past the hard-coded literal. Update the literal at line 211/220/229/238. If they churn often, switch the number assertion to a shape match such as /[\d,]+\+/.
"Found 0 course cards" / card count fails The content API did not return in time, or genuinely returned nothing. Check whether the Certificate-badge test (which waits up to 15 s) also failed. If it passed and the count test did not, it is the instantaneous count() — give tests 3 and 5 the same toBeVisible-then-count shape.
Broken-images test lists thumbnails Real 404s in the course-thumbnail CDN, or images that failed to decode. The failure message names every URL. Open one directly — the lazy-loading and in-flight cases are already filtered out, so anything listed genuinely returned nothing.
Console-errors test fails A genuine uncaught JavaScript error — resource 404s are already filtered. Read the console.warn line printed before the failure; it carries the exact messages. This one is rarely a test problem.
Load-time test fails intermittently The 10 s budget is measured to domcontentloaded; a cold CDN or a slow network can exceed it. Check the logged milliseconds across recent runs before changing anything. A steady creep is a real regression; one outlier is not.
A logo or social test passes but you know the element is gone Working as designed — it is one of the 22 soft tests. Check the console for the missing ✅ line. If that element must gate the build, remove its if (await safeScroll(...)) guard and let the assertion run unconditionally.
"View All" clicks the wrong section The two View All links are addressed by position — .first() for Top Courses, .nth(1) for CNE. If a third carousel is added, or the sections are reordered, these indices need revisiting. Scope the locator to the section container instead of indexing the whole page.
Hero carousel tests log "skipping" every run The rotation timing never lands on that slide while the test looks. Expected behaviour today. To make it deterministic, click the relevant carousel dot to pin the slide before asserting, rather than hardening the assertion as written.
The one rule to keep Every text assertion in this file goes through tr(), and every element locator names two or three alternatives. Both habits exist for the same reason: this page's language, content and markup all change independently of its behaviour. When you add a check, match the structure and accept either language — and when you make something hard rather than soft, do it because the element is guaranteed, not because green feels better.
