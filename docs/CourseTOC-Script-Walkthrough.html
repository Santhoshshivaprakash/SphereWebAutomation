1   What this script does

It is the sweep of the course overview page — the screen a learner lands on after searching for and opening a course, and the screen they come back to between every module.

The URL shape is /app/toc/<courseId>/overview, and the page carries a lot: the course title and its metadata badges, three action icons, the Start/Resume banner, three tabs, a description, and a licence block. This spec puts one granular test on each of those elements — 21 tests in five groups — so a failure names the exact control that broke rather than "the course page".

Its scope was carved out of the course-completion suite CourseComplete.spec.ts drives a whole course end to end and deliberately does not click around the overview page, because doing so disturbs the Resume state it depends on. Its comment at line 2211 says as much: "the full overview element sweep lives in CourseTOC.spec.ts now." This file is that sweep, and the separation is why both can be trusted.

Two inputs, both required

InputWhy it is needed
a logged-in sessionThe TOC is behind auth. The suite imports test from ./helpers/authedTest (line 21), so every test arrives with a logged-in context already established.
COURSE_NAMELine 28. There is no default. Without it, beforeEach calls test.skip() on line 223 and all 21 tests skip — they do not fail, and they do not run against a blank page.

That second point matters when reading a report: 21 skipped is the signature of a missing COURSE_NAME, not of a broken page. The skip message says so explicitly — "Set COURSE_NAME to run Course TOC coverage".

How a test gets to the page

Every test starts from the home page and searches. There is no hard-coded course URL anywhere in the file, because course ids differ per environment. searchAndOpenCourse() (line 47) types the name into the search box, presses Enter, and clicks the first result whose title starts with the same 8 characters — a prefix match, because result cards truncate long titles.

Once one test has opened the course, the URL is cached in tocUrl (line 197) and every later test takes a much cheaper path: navigate straight there, verify it landed, done. Section 3 diagrams both paths and the verification between them.

Three minutes per test Line 194 sets test.setTimeout(3 * 60 * 1000). That is not defensive padding — the banner alone is allowed 90 seconds (Section 3), and a slow-path re-open makes up to three trips through search before giving up. A 30-second default would fail this suite on a healthy site.

Everything this suite touches lives on one screen. The five groups in the source map cleanly onto five bands of that screen, top to bottom.

Why the groups run top to bottom It is not a coincidence. The file is ordered the way a person reads the page, so when a report shows five consecutive failures you can read them as "everything below the banner is missing" rather than having to reconstruct which control lives where.

3   The readiness model

This is the idea the whole file is built on: the tabs appearing does not mean the page is ready. Everything else — the 90-second timeout, the two-stage gate, the fast and slow paths — follows from that one measurement.

The TOC overview paints in layers. The shell and the tabs come from the course metadata and are on screen in well under a second. The Start/Resume banner is different: it waits on the enrolment and progress calls, so it is the last thing to appear. On a clean load that is 1.6 to 2.8 seconds. Coming back from the player — which is exactly what a learner does between modules — it has been measured at around 70 seconds.

The bug this replaced The original tests used a plain expect(banner).toBeVisible(), which carries Playwright's default 10-second window. On a clean load it passed. After a round trip through the course player it failed every time — while the page was still painting correctly. The suite was reporting a product failure that was really a test failure.

3   The readiness model (continued)

Why isVisible() could not be used for the gate

The comment at lines 204–207 records a real regression. onToc() originally used isVisible() to check for the tabs. That call does not wait — its timeout option is ignored, and it answers about the current instant only. Used milliseconds after a goto, it reported "not the TOC" on a page that was about to render perfectly, and sent every test down the slow re-open-via-search path. The suite still passed; it just took several times longer than it needed to.

The fix is the .then(true).catch(false) idiom on line 213 — it turns a waitFor() into a boolean without letting the rejection escape:

// line 212-213 — a wait that answers yes/no instead of throwing
const tabs = await page.getByText(/^(Details|Overview|Modules)$/i).first()
  .waitFor({ state: 'visible', timeout: TABS_READY_MS }).then(() => true).catch(() => false);

The three timeouts are three different questions

It would be simpler to have one banner timeout. There are three because they answer different questions, and collapsing them would make the suite either slow or flaky.

ConstantDefaultThe question it answers
BANNER_TIMEOUT
line 34		90 s"How long may the banner take before we call it broken?" Used after a fresh open, where there is no fallback left — so it has to cover the ~70-second worst case with headroom.
BANNER_READY_MS
line 37		30 s"Is the cached URL good?" Deliberately shorter, because a failure here is cheap — it just falls through to the slow path. Waiting the full 90 seconds to discover the cache is stale would be wasted time.
TABS_READY_MS
line 39		10 s"Is this even a rendered TOC?" The tabs paint in under half a second, so 10 seconds is already twenty times the observed value — it exists to fail fast on a wrong page, not to wait for a slow one.
SLOW_BANNER_MS
line 41		10 sNot a timeout at all. "Was this slow enough that a human should know?" Crossing it prints a 🐢 line and nothing else. Section 11 explains how to mine those lines out of a run.

All four read from the environment, so a slow CI box can be given more room without editing the file:

# give the banner three minutes and raise the slowness bar to 20 s
$env:TOC_BANNER_TIMEOUT="180000"; $env:TOC_SLOW_BANNER_MS="20000"; npm run run:course-toc

The banner button changes element type as you learn

This is the other discovery in the file, and it is documented at length in the doc-comment above startOrResumeBtn() (lines 86–100). The same visual control is emitted as two different elements depending on progress:

Learner stateWhat the DOM actually contains
Not started, or in progress<button class="banner-btn">Start | Resume</button>
100% complete<a class="banner-btn resumeButton">Start Again</a>
Verified on staging: 0 matches as a link, 1 via .banner-btn On a completed course getByRole('button') finds nothing, because the control is no longer a button — and the link role does not rescue it either: the measurement recorded in the source is zero matches as a link against one match via the class. Neither role is dependable, so startOrResumeBtn() puts .banner-btn first and keeps both roles behind it as belt-and-braces. The failure this prevents is the most awkward kind: it appears only on accounts that have finished something. 
// line 101-107 — class first, roles as a fallback, .first() to stay strict-mode safe
function startOrResumeBtn(page: Page): Locator {
  return page.locator('.banner-btn, [class*="resumeButton"]')
    .or(page.getByRole('button', { name: /^(resume|start|start again)$/i }))
    .or(page.getByRole('link',   { name: /^(resume|start|start again)$/i }))
    .first();
}

4   Helpers and harness

Seven helpers sit between the tests and the page. They exist so that a test body can read as one sentence about one control, and so that a markup change is fixed in one place rather than twenty.

HelperLineWhat it does, and the problem it solves
searchAndOpenCourse47 Types COURSE_NAME into the home search box, presses Enter, and clicks the first result. Two details matter: it matches on the first 8 characters only, because result cards truncate long titles; and it treats a changed URL as the proof that the click opened something, rather than trusting the click.

waitForBanner110 Waits for that control and returns how long it took in milliseconds, or -1 if it never appeared. Returning a number rather than a boolean is what lets the caller distinguish "fine", "slow enough to report", and "broken" — see the 🐢 line in Section 11.
startOrResume125 Actually clicks the control, trying six locators in order and stopping at the first visible one. Returns whether the URL changed. Its last resort (line 151) is a URL test for /viewer/, /play/ or /learn/ — if we were already inside the player, that counts as success.
closeAnyPopup157 Best-effort dismissal. Tries five shapes of close button in one selector, falls back to the Escape key, then waits 400 ms for the dialog animation. Its timeouts are deliberately tiny (700 ms to look, 1500 ms to click) because this is cleanup, not a check.
actionIcon178 Finds a div.toc-icon-action and narrows it by label text. Exists because the click handler is on the wrapper div, not the label span inside it.
skipIfAbsent265 Logs ⏭️ and calls test.skip() when an optional control is missing. Declared inside the describe block because test.skip(true, …) only works from within a test's scope.

Alongside them is one constant, POPUP (line 185), which lists six container shapes in a single selector string:

'[role="dialog"], .cdk-overlay-pane, .mat-mdc-dialog-panel, [class*="modal"], [class*="popup"], [class*="dialog"]'

Angular Material has changed its dialog class names across versions, and the app mixes hand-rolled overlays with Material ones. Listing all six means a rename in any single shape does not break the four popup tests at once.

Deliberately self-contained The banner above the helpers (line 44) says "self-contained so this file is independent of CourseComplete". searchAndOpenCourse, startOrResume and closeAnyPopup all have cousins in the completion suite. Duplicating them was the choice: the completion suite's versions are tuned for driving a course to the end, and coupling the two files would mean a change made for one silently altering the other.

How the suite gets a logged-in page

Line 21 imports test and expect from ./helpers/authedTest rather than from Playwright directly. That harness picks an auth mode from the environment, first match winning:

#TriggerHow it authenticates
1USE_CDP=1Attaches to a Chrome you are already logged into, over the DevTools protocol. The local-development mode — on localhost, cookie injection returns 419, so this is the only thing that works. No storageState file is written, and the harness never closes a browser you own.
2USE_FRESH_USER=1Reuses the session of an account minted by the create-account suite, from .auth/fresh-user.json. Falls back to credential login with a warning if that file is missing.
3a saved state fileLoads a previously captured storageState.
4TEST_USER_EMAIL + TEST_USER_PASSWORDDrives a real UI login once, saves the state, and hands every test a context built from it. This is what CI uses against staging and production.

If none of the four is configured the harness throws immediately with a message listing all of them — it fails in setup rather than running 21 tests against a login screen.

Not serial, on purpose

Line 191 carries a one-line note that is easy to skip past: "NOT serial — each test resets to the TOC in beforeEach, so one failure must not skip the rest."

That is a real trade. test.describe.serial would let the tests share a single page load and run much faster. But under serial, the first failure aborts every test after it — so a broken Details popup would hide the fact that the licence block is also missing. Here, each test pays the cost of returning to a known state and, in exchange, a report of 21 results is 21 independent facts.

The tests do still share one thing: tocUrl (line 197), the cached course URL. It is a performance cache, not shared state — every test re-verifies it through onToc() before trusting it, and silently re-opens the course if it has gone stale.

One test self-heals mid-body Line 388, in the Resume/Start test, re-checks onToc(page) and navigates back if needed. That is there because in CDP mode the browser belongs to a human — a stray click in the window the tests are driving can move the tab off the TOC between beforeEach and the assertion.

Anchored versus unanchored

Three of the five regexes above are anchored; two are not. The rule — which holds across every group that follows — is that an anchor goes on text short and common enough to appear inside other text (By:, Details, Overview), and is left off where the pattern is already specific, as with the duration formats.

Why every test here scrolls first

Both sections sit below the fold on a normal viewport, and scrollIntoViewIfNeeded() appears before each assertion. It is worth being precise about what that call is and is not for.

Playwright's toBeVisible() does not require an element to be inside the viewport — it checks that the element is attached and has a non-empty bounding box. So the scroll is not there to satisfy the matcher. It is there because the app renders parts of this page lazily: content below the fold can be absent from the DOM until something scrolls toward it. Scrolling first turns "not rendered yet" into "rendered", which is the state the test actually means to check.

Each scroll has its errors swallowed with .catch(() => {}). If the element is already in view, or the page is short enough that there is nothing to scroll, that is not a failure — and letting the scroll throw would replace a clear "Description not visible" with a confusing scroll error.

Test 18 reads the href and then does nothing with it The last line prints href, which is the one piece of information worth checking — a Creative Commons link that points somewhere else is a licensing problem, not a cosmetic one. Adding expect(href).toContain('creativecommons.org') after the skip guard would cost nothing and would turn a printed string into a checked fact. As written, the test proves only that a link matching one of two patterns exists.

Three locator techniques worth stealing

  1. Register the listener before the click, in one call. Test 19 uses Promise.all([ waitForEvent('popup'), author.click() ]). The popup promise is created first, so the listener is attached before the click can fire — a tab that opens instantly is not missed. Awaiting the click first and then waiting for the popup is the classic race, and it fails intermittently rather than always.
  2. Climb from the icon to its button. Material icons render their name as ligature text inside a <mat-icon>, so the thing you can find by text is not the thing you can click. Test 20's third fallback, locator('xpath=ancestor-or-self::button[1]'), walks up from the matched icon to the nearest enclosing button — and ancestor-or-self rather than ancestor covers the build where the icon is the button.
  3. Handle both tab shapes with one line. const target = popup ?? page. If a new tab opened, assert against it; if the app navigated in place, assert against the same page. Everything after that line is identical, so the test does not fork.
Test 21 cannot fail — and it is the one that matters most startOrResume() returns true only if the URL actually changed (or we were already in the player). So started === false means the learner could not start the course — the single most serious thing this page can get wrong. The test passes that value to skipIfAbsent(), which skips. A broken Start button therefore produces a skipped test, not a red one, and a skip in a report of 21 is easy to read past.

The fix is one line: replace the guard with expect(started).toBe(true). The skip idiom is right for the Creative Commons link, which genuinely may not exist on a given course; it is wrong here, because every course has a way in. That change would take the file from 15 unconditional assertions to 16, and would make the suite fail loudly on the defect a learner would notice first.

Tests 19 and 20 use the same guard more defensibly. A course with no linked organisation is a real content state, and some builds of the shell render no back control at all — skipping on those is correct. But both of those tests then go on to assert properly, which is the difference: their guard decides whether to check, not what to conclude.

10   What green actually proves

Twenty-one green ticks are not twenty-one guarantees. Here is exactly what each one is worth.

The honest summary

Green means this, for certain
  • The course opened from a search by name
  • Title, CNE hours, duration, review count and author all rendered
  • All three action icons are present and clickable
  • Details opens and closes
  • Certificate responds with something
  • Share reveals share options
  • The banner rendered within 90 seconds
  • All three tabs are present
  • The module list is non-empty
  • Description and licence blocks rendered
Green does not mean this
  • That the star rating rendered — only the (n) count is checked
  • That the Discussion tab shows anything
  • That the Creative Commons link points at creativecommons.org
  • That a learner can start the course — test 21 skips instead of failing
  • That the author link or back icon exist — both skip when absent
  • That the banner was fast. Slowness is logged, never failed
  • That any of the popups contain correct content — only that they appear

What each shape of failure means, in the order you are most likely to meet it.

SymptomCauseFix
All 21 tests skipped, none red COURSE_NAME is not set. beforeEach skips at line 223 before doing anything else. Set it. A configuration state, not a defect — but it reads as a clean run in a summary count, so check the skip total before trusting green.
Error: Could not open course "…" on every test Three search attempts all failed (line 250). Either the name does not match anything on this environment, or the home search box never rendered. Check the exact title on the target environment: the match is on the first 8 characters, so a changed prefix breaks it. Confirm BASE_URL.
↻ TOC not loaded from cached URL before every test onToc() keeps returning false. Usually the session expired and the app is redirecting to login, so the URL never matches /toc/…/overview. Re-authenticate. In CDP mode log the attached Chrome back in; otherwise delete the stale storageState file so the harness logs in again.
⚠️ Banner never rendered, then test 12 fails The enrolment or progress call is failing or timing out. The banner is the only element that depends on it. Watch the network panel on the URL from the 📌 line. Slow-but-successful calls mean raising TOC_BANNER_TIMEOUT; failing ones mean the test is right.
Banner test passes but prints 🐢 on every run Real slowness. Most often seen on the run right after a course has been opened and exited. Not a test fix. Report the number — that is what the line exists for.
Test 8 or 10 fails: the popup opened but would not close closeAnyPopup()'s five close-button shapes no longer match, and Escape did not dismiss the dialog either. Add the dialog's close-control shape to the selector at line 161. Fix it properly rather than reaching for Escape — a dialog a user cannot close is the bug this test exists to find.
An action-icon click appears to do nothing The click landed on the label span instead of the div.toc-icon-action wrapper that carries the handler. Use actionIcon(). Do not "simplify" it to getByText('Details').click() — that is the exact regression it was written to prevent.
The banner locator finds nothing, only on one account That account completed the course, so the control is now an <a class="banner-btn resumeButton">Start Again</a> and neither role matches. Keep .banner-btn first in the locator chain. See Section 3.
Test 14 fails: expected > 0, received 0 The module list is genuinely empty — the content hierarchy did not load. A real defect, and the most valuable failure this suite produces. Confirm by opening the 📌 URL and clicking Modules by hand.
strict mode violation: resolved to N elements A .first() was dropped from a locator during an edit. Put it back. Every locator in this file ends in .first() for exactly this reason.
Passes headed locally, fails in CI CDP mode has no live Chrome to attach to on a build agent. CI should use mode 4 — TEST_USER_EMAIL and TEST_USER_PASSWORD. Leave USE_CDP unset there.
Tests 19 and 20 skip on every course Either the courses genuinely have no linked organisation and no back control, or .blue-link / ws-widget-btn-page-back were renamed in the shell. Check one course by hand. If the controls are visibly there, the selectors are stale — and a permanently-skipping test is worse than a failing one, because nothing draws attention to it.
